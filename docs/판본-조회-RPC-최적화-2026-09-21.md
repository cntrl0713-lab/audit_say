# 판본 조회 RPC(`cpa_get_question_version`)의 비용과 최적화 방안

2026-09-21 r33~r40 운영 반영의 독립 검증이 두 번 모두 `READ_RPC_FAILED_500`으로 멈췄다. 원인을 좁힌 결과 무결성 위반이 아니라 **statement timeout**이었고, 그 뿌리는 이 RPC의 비용이 릴리스 누적에 비례해 커지는 구조다. 이 문서는 측정치와 대응 방안을 정리한다.

## 1. 관측

- 두 실행(`02-verify`·`03-verify`)이 각각 329초·303초에 실패했고 로그는 `READ_RPC_FAILED_500` 한 줄뿐이다. 검증기는 상태 코드만 남기고 응답 본문을 버린다.
- 읽기 전용 진단(`db-import/diagnose-verify.mjs`)으로 343판본을 같은 순서로 전부 조회한 결과:

| 항목 | 값 |
| --- | --- |
| 조회한 판본 | 343 |
| 성공 | **340** |
| 실패 | **3** (position 181·187·188) |
| 오류 코드 | 전부 `57014` — `canceling statement due to statement timeout` |
| 실패한 세트 | `std-points-20260914-ac4f0f2444b0`·`-a0ae425fd0b3`·`-c2f71f331a7b` |

- **무결성 위반은 0건**이다. RPC가 던지는 25가지 예외는 하나도 걸리지 않았다.
- 소요 시간은 이전 일곱 릴리스에서 279~356초였고 371세트일 때도 347초로 통과했다. **세트 수는 원인이 아니다.**

## 2. 비용 구조

`cpa_get_question_version`은 `cpa_get_question_version_with_source_metadata`를 감싼다. 그 함수는 **해당 판본이 묶인 모든 릴리스를 순회**하며(`supabase/migrations/20260912060000_cpa_private_source_metadata.sql` 20~57행) 릴리스마다 세 가지를 한다.

1. `sha256(convert_to(r.source_document,'UTF8'))` — 저장 원문 **전체**를 해시
2. `r.source_document::jsonb` — 저장 원문 **전체**를 파싱
3. `jsonb_array_elements(...) with ordinality` — 배열을 훑어 해당 세트 하나를 찾음

즉 한 번의 호출 비용이 **O(R × D)**다. R은 그 판본이 묶인 릴리스 수, D는 저장 원문 크기다.

| 기호 | 현재 값 |
| --- | --- |
| D (저장 원문) | 약 **6.2 MB** |
| R (릴리스 누적) | 기록된 것만 **22개** (오늘 하루에 4개 증가) |
| 최악 호출 | 22 × 6.2 MB ≈ **136 MB**의 해시·파싱 |
| 검증 한 번 | 343회 호출 × 평균 R × D ≈ **수십 GB** |

## 3. 왜 하필 그 세 세트인가

실패한 셋은 5~10 KB짜리 작은 세트이고 물음 1~2개, criterion 2~4개다. **세트 자체의 크기는 원인이 아니다.**

차이는 **R**이다. 2026-09-19 기준서형 정답 암시 검토가 180여 세트에 새 판본을 만들면서 그 세트들의 R이 초기화되었다. 그때 고쳐지지 않은 세트는 2026-09-14 판본을 그대로 유지해 **지금까지 모든 릴리스에 묶여 있다.** 실패한 셋이 바로 그런 판본이다.

그러므로 이 실패는 앞으로 릴리스를 더할수록 **더 많은 판본으로 번진다.** 한 번의 재시도로 해결되지 않는다.

## 4. 대응 방안

### 방안 1 — 검증 경로의 statement timeout 상향 (임시)

함수의 `set` 절에 `statement_timeout`을 두거나 검증기 연결에서 올린다. 한 줄 변경으로 지금 막힌 것을 푼다.

- **장점**: 가장 빠르고 위험이 낮다.
- **한계**: R이 릴리스마다 1씩 늘어 **시간을 벌 뿐 구조를 고치지 않는다.** 단독으로 채택하지 않는다.

### 방안 2 — 중복 검사 제거 (무료)

50~52행의 "ambiguous across releases"(릴리스 간 `normalized_source` 동일성) 검사는 **증명상 불필요하다.** 47~49행이 모든 릴리스에 대해 `candidate_hash = v.content_hash`를 요구하고, `candidate_hash`는 `normalized_source`와 `applicability`에 대한 sha256이다. 모든 릴리스가 같은 `v.content_hash`를 통과했다면 `normalized_source`는 구성상 동일하다.

- **장점**: 릴리스마다 jsonb 전체 비교 한 번을 없앤다. 동작이 바뀌지 않는다.
- **한계**: 지배적 비용(해시·파싱)은 줄지 않는다. 방안 3과 함께 적용한다.

### 방안 3 — 릴리스 문서 해시 검증을 판본마다 반복하지 않기 (권장, 즉시)

`sha256(source_document) = source_file_hash`는 **릴리스의 성질이지 판본의 성질이 아니다.** 지금은 343판본 × 22릴리스만큼 같은 문서를 되풀이해 해시한다.

릴리스당 한 번만 확인하고 결과를 남긴다. 작은 불변 표 하나면 된다.

```sql
create table public.cpa_question_bank_release_document_verified (
  release_id uuid primary key references public.cpa_question_bank_releases(id),
  source_file_hash text not null,
  verified_at timestamptz not null default now()
);
```

RPC는 이 표에 기록이 있고 해시가 같으면 재계산을 건너뛴다. 기록이 없으면 지금처럼 계산하고 기록을 남긴다(최초 1회).

- **장점**: 지배적 비용의 **약 절반**을 없앤다. 기존 검사의 의미를 유지한다(릴리스 문서는 여전히 한 번은 검증된다).
- **주의**: 표가 비어 있어도 정확성이 유지되도록 "기록 없으면 계산"을 기본으로 둔다.

### 방안 4 — (판본, 릴리스) 바인딩 메모화 (근본, 중기)

import 시점에 이미 문서를 메모리에 들고 있으므로, 릴리스 항목마다 **추출된 세트와 위치**를 저장한다.

```sql
create table public.cpa_question_bank_release_item_source (
  release_id uuid not null,
  set_version_id uuid not null,
  source_position bigint not null,
  normalized_source_sha256 text not null,
  primary key (release_id, set_version_id)
);
```

RPC는 문서를 전혀 파싱하지 않고 이 행들만 읽어 위치·해시를 대조한다. 비공개 메타데이터 복원에 필요한 `source_set`은 **가장 최근 릴리스 하나**에서만 꺼내면 된다.

- **장점**: **O(R × D) → O(R) + O(D 한 번)**. 릴리스가 늘어도 비용이 늘지 않는다. 구조적 해결이다.
- **비용**: 스키마 변경과 **import 경로 변경**이 필요하다. import RPC는 과거 receipt가 해시로 고정하므로 **새 실행 버전**에서 도입하고, 과거 기록은 옛 형상을 그대로 읽을 수 있어야 한다.
- 기존 릴리스의 메모 행은 한 번의 백필 작업으로 채운다(읽기 전용 계산 + 쓰기 1회).

### 방안 5 — `source_document`를 `jsonb`로 함께 보관

지금은 `text`라 읽을 때마다 파싱한다. `jsonb` 컬럼을 병행 보관하면 파싱 비용이 사라진다. 다만 sha256은 **원문 바이트**에 대한 것이라 `text`를 버릴 수 없다.

- **장점**: 파싱 비용 제거.
- **한계**: 저장 용량이 늘고 해시 비용은 남는다. 방안 3·4보다 이득이 작다.

### 방안 6 — 검증 범위 축소 (권장하지 않음)

검증기가 매번 343판본을 전수 조회하는 대신 이번 릴리스에서 새로 묶인 판본과 표본만 본다.

- **한계**: 독립 검증의 보장을 약화시킨다. 이 저장소의 원칙("실패를 분모에서 빼지 않는다", "빌드 통과를 검수 완료로 보고하지 않는다")과 어긋난다. **기록해 두되 채택하지 않는다.**

## 5. 권고 순서

1. **방안 2 + 방안 3**을 한 migration으로 적용한다. 동작을 바꾸지 않으면서 지배적 비용의 절반을 없애고, 지금 막힌 검증을 통과시킬 가능성이 높다.
2. 그래도 모자라면 **방안 1**을 같은 migration에 더해 시간을 번다.
3. 다음 import 실행 버전을 만들 때 **방안 4**를 도입해 구조를 끝낸다. 그 시점에 기존 릴리스 백필도 함께 한다.

## 6. 이번 릴리스(`92948c50`)의 처리

반영 자체는 커밋되었고 **왕복 검증을 통과**했다(343세트·473물음·1,753점, 퇴역 8·추가 10, 학습 단위 407). 실패한 것은 읽기 전용 2차 검증이고 그 실패도 데이터 결함이 아니라 조회 성능이다.

그러나 **독립 검증을 얻지 못했으므로 `completion.json`을 쓰지 않았다.** 위 migration을 적용한 뒤 `db-import/verify-v2.mjs`를 다시 실행해 검증을 마치고 완료 기록을 남긴다. 실패한 `02-verify`·`03-verify`의 로그와 결과, 그리고 `diagnosis-v1.json`은 모두 보존한다.

migration 적용은 운영 DB 변경이므로 **사용자가 직접 실행**한다. agent는 migration과 실행 순서만 준비한다.
