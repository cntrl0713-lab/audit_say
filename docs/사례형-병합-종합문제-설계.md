# 사례형 병합 종합문제 설계

미갱신 사례형 문제를 주제·사실이 이어지는 것끼리 묶어 종합문제로 대체하는 설계다. 2026-09-20 기준이며 수치는 그날 정본에서 집계했다. A등급 4묶음은 같은 날 r16~r19로 제작·설치를 마쳤고(정본 354세트), 이 문서는 남은 등급의 계획으로 이어진다. 개별 회차의 실행 기록은 [검토 장부](../cpa_uploader/analysis/reviews/case-review-2026-09-15/README.md), 문항 규칙은 [사례형 발문과 절차 선택형](물음별-학습-단위와-분류-계약.md#사례형-발문과-절차-선택형)과 [공통 배점 계약](물음별-학습-단위와-분류-계약.md#배점과-물음별-타당성)을 따른다. 이 문서는 후보 선정과 설계 방침만 다루고, 실제 제작·검증 절차는 [제작 스킬](../.agents/skills/audit-question-author/SKILL.md)·[검토 스킬](../.agents/skills/audit-question-review/SKILL.md)에 있다.

## 1. 현재 상태

- 사례형 부모 51개·132물음(2026-09-20 r16~r19 설치 후). 그중 [수정 요청서](case-question-edit-notes-2026-09-14.md)의 갱신 대상으로 남은 것이 **31개**다(A등급 4묶음 9개를 처리한 뒤의 수). 처음 이 문서를 쓸 때는 40개였다.
- 갱신이 끝난 것은 r01~r19의 20세트다. `pilot-01-005`는 2026-09-18에 종합문제로 따로 대체했다.
- 남은 31개 중 4개는 한 세트 안에 기준서형 물음이 섞여 있다(4·17·40·41번. 15번은 r17에서 분리 보존했다). 병합할 때 그 물음은 별도 기준서형으로 분리하거나 퇴역 범위에 포함할지 먼저 정한다(r07이 `pilot-02-006`의 기준서형 물음 1을 함께 퇴역시킨 선례가 있고, r17은 반대로 `pilot-07-006` sub4를 `pilot-07-006-standards-20260920`으로 분리 보존했다. 2026-09-20 사용자 결정은 **분리 보존**이다).

## 2. 묶음을 고르는 기준

1. **한 회사의 사실 하나로 묶이는가.** 회사·역할·보고기간·통제 상태를 새 공통 사실에 맞출 수 있어야 한다. 전제가 충돌하면 한쪽을 고치고 계보에 남긴다.
2. **원출처가 같거나 요소가 이미 중복인가.** 같은 기출 요소에 연결된 세트, 서로의 요소를 재사용하는 세트를 합치면 중복이 사라진다.
3. **단계가 이어지는가.** 계획 → 수행 → 종결처럼 시간 순서로 배치할 수 있으면 물음 분할이 자연스럽다.
4. **같은 기준에서 결론이 갈리는 두 경우가 없는가.** 있으면 한쪽만 함정·옳지 않은 항목으로 남기고 다른 쪽은 삭제한다. 이 판단이 병합의 최대 제약이다.
5. **크기.** 2~3물음·7~12점이 기존 회차의 실적 범위다. 2물음·4~7점짜리 작은 세트를 우선 묶고, 이미 3물음·8~10점인 세트는 발문 형식만 바꿔도 종합문제 형태가 된다.

## 5. 병합 설계 체크리스트

- **항목 구성**: 옳은 절차·판단과 옳지 않은 절차·판단을 번호로 섞고, 물음마다 옳지 않은 것을 모두 고르게 한다. 옳지 않은 항목 수는 밝히지 않고 물음마다 다르게 둔다. 함정(틀려 보이나 기준상 허용되는 항목)이 옳다는 것도 원문으로 확정한다.
- **배점**: 물음마다 식별 1점 + 옳지 않은 항목마다 이유 또는 보완절차 1점. 구체적 후속절차 나열을 득점 요건으로 삼지 않는다. 한 항목에 독립된 잘못이 둘이면 점수를 늘리지 말고 항목을 나눈다.
- **정답 암시 금지**: 사실관계·발문·제목·태그가 결론·위반 사유·누락 절차를 알려 주지 않는다. 옳지 않은 항목에만 근거를 붙이거나 같은 근거를 되풀이하지 않는다.
- **대조되는 두 경우**: 원 세트들이 같은 기준에서 반대 결론을 정답으로 삼고 있는지 먼저 대조한다. 있으면 한쪽만 남기고 삭제한 요구를 계보에 적는다. r12·r13이 실제로 이 문제를 만났다.
- **전제 통일**: 회사·역할·보고기간·통제 상태·기록 방식을 하나로 맞추고, 바뀐 전제에서 승계한 항목의 옳고 그름이 여전히 성립하는지 근거 문단으로 재확정한다.
- **연도**: 20X1·20X2만 쓴다(대상 연도 2027년의 적용 판본은 `verification.notes`에 실제 연도로 기록).
- **출처**: 원 세트의 인용을 바이트·`content_hash` 그대로 재사용하는 것을 기본으로 하고, 새 인용은 등록된 공식 전문에서 발췌해 파일·행 범위를 남긴다.
- **중복 검토**: 이미 갱신된 세트와 요구가 겹치지 않는지 대조해 design의 중복 검토에 적는다. r13은 r12의 "자료 신뢰성" 요건과 갈라 두기 위해 인용 기준서를 달리했다.

## 6. 회차 실행 절차

1. 원 세트와 근거 기준서 원문을 읽고 항목별 옳고 그름·근거 문단·배점 대응표를 확정한다(`design.json`, `lineage.json`).
2. `build-draft.mjs`로 `sets.json`을 만들고 `validate_draft_v3.ts --file … --against-bank`로 형상·인용·ID·발문 충돌을 검사한다.
3. 현재 정본 + 초안을 메모리에서 `validateAuthoringBank`로 검증하고 분류·카탈로그를 컴파일한다(정본 파일은 쓰지 않는다).
4. agent 내용 검토를 기록한다(`root-content-review-v*.json`). 미해결 발견사항이 남으면 게시하지 않는다.
5. 대표 사례(모범·부분·오답)를 **채점 전에** `qa.json`에 확정하고, dry run 뒤 Luna 대표 3요청으로 실측한다. 물음별 ±1점 허용, 0점끼리의 판정 상태 차이는 재채점하지 않는다.
6. 수락 batch → 격리 stage 승급·게시 → 정본 설치 → coverage 재연결 → wiki 퇴역·재생성 → 장부 갱신 → 운영 증분 릴리스.

## 7. 실행에서 걸렸던 것 (다음 회차 주의)

- **발문 바이트 중복**: `validateAuthoringBank`는 은행 전체에서 발문 문자열이 같으면 거절한다. "자료 N의 …" 같은 정형 발문은 다른 회차와 충돌하기 쉬우므로 단계 이름을 넣는다. r15가 이 문제로 v2를 다시 만들고 최종 발문으로 재실측했다.
- **criterion id**: 세트 안에서 고유해야 한다. 물음마다 같은 id를 쓰면 채점 모델이 잘못된 id를 돌려준다.
- **정본 해시 조율**: 후보 은행 빌드는 분류 카탈로그의 `source_file_sha256`과 정본 해시가 같아야 통과한다. 다른 세션이 정본을 설치하는 중이면 빌드를 미룬다.
- **승급과 커밋의 충돌**: pre-commit 전체 테스트가 실제 정본·장부 파일이 바뀌지 않는지 감시한다. 승급·설치가 도는 동안에는 커밋이 실패한다.
- **운영 명령**: 자동 모드 분류기가 릴리스 드라이버 실행을 막는다. `--prepare`·`--probe`·`--apply`는 사용자가 직접 실행하고, agent는 준비·기록만 맡는다.
- **기준 원문**: 다른 세션이 정본에만 설치한 변경이 있으면 정본이 운영 릴리스보다 앞선다. 증분 릴리스의 기준 원문은 활성 릴리스와 바이트가 같은 판본(예: HEAD 커밋의 정본)으로 잡고, 앞선 변경을 릴리스 범위에 포함할지 사용자에게 확인한다.
- **기준서형 세트를 함께 추가할 때**: 운영 반영 드라이버가 새 세트의 학습 단위를 `<세트ID>--case`로만 찾는다. 기준서형은 물음마다 `<세트ID>--<물음ID>--standard`이므로 r19까지의 드라이버를 그대로 쓰면 apply가 커밋된 뒤 이 단정에서 멈춘다(r16~r19에서 실제로 발생, 재개 스크립트로 처리). 다음 회차에서 기준서형을 추가하면 드라이버의 단위 확인을 유형별로 먼저 고친다.
