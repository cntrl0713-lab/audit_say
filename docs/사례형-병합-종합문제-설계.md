# 사례형 병합 종합문제 설계

미갱신 사례형 문제를 주제·사실이 이어지는 것끼리 묶어 종합문제로 대체하는 설계다. 2026-09-20 기준이며 수치는 그날 정본에서 집계했다. A등급 4묶음은 같은 날 r16~r19로 제작·설치를 마쳤고(정본 354세트), B등급 8묶음도 2026-09-21에 r20~r27로 마쳤다(정본 346세트, 운영 release `c04d6bdd`). 이 문서는 남은 C·D등급의 계획으로 이어진다. C등급 5묶음도 같은 날 r28~r32로 마쳐(정본 341세트, 운영 release `04052784`) 남은 것은 D등급뿐이다. D등급 8개도 같은 날 r33~r40으로 마쳐(정본 343세트, 운영 release `92948c50`) 대상 40개를 모두 처리했다. 개별 회차의 실행 기록은 [검토 장부](../cpa_uploader/analysis/reviews/case-review-2026-09-15/README.md), 문항 규칙은 [사례형 발문과 절차 선택형](물음별-학습-단위와-분류-계약.md#사례형-발문과-절차-선택형)과 [공통 배점 계약](물음별-학습-단위와-분류-계약.md#배점과-물음별-타당성)을 따른다. 이 문서는 후보 선정과 설계 방침만 다루고, 실제 제작·검증 절차는 [제작 스킬](../.agents/skills/audit-question-author/SKILL.md)·[검토 스킬](../.agents/skills/audit-question-review/SKILL.md)에 있다.

## 1. 현재 상태

- 사례형 부모 51개·132물음(2026-09-20 r16~r19 설치 후). 그중 [수정 요청서](case-question-edit-notes-2026-09-14.md)의 갱신 대상으로 남은 것이 **31개**다(A등급 4묶음 9개를 처리한 뒤의 수). 처음 이 문서를 쓸 때는 40개였다.
- 갱신이 끝난 것은 r01~r19의 20세트다. `pilot-01-005`는 2026-09-18에 종합문제로 따로 대체했다.
- 남은 31개 중 4개는 한 세트 안에 기준서형 물음이 섞여 있다(4·17·40·41번. 15번은 r17에서 분리 보존했다). 병합할 때 그 물음은 별도 기준서형으로 분리하거나 퇴역 범위에 포함할지 먼저 정한다(r07이 `pilot-02-006`의 기준서형 물음 1을 함께 퇴역시킨 선례가 있고, r17은 반대로 `pilot-07-006` sub4를 `pilot-07-006-standards-20260920`으로 분리 보존했다. 2026-09-20 사용자 결정은 **분리 보존**이다).
- (2026-09-21 갱신) B등급 8묶음을 r20~r27로 처리한 뒤 사례형 부모 42개·109물음이고, 갱신 대상으로 남은 것은 **14개**다(C등급 6개·D등급 8개. 8절 참조). 17번의 기준서형 물음은 같은 정책으로 `pilot-11-005-standards-20260921`에 분리 보존했으므로, 기준서형이 섞여 있는 남은 세트는 4·40·41번 셋이다.
- (2026-09-21 갱신, r28~r32) C등급 5묶음(요청서 1·4·37·38·62·70번)을 처리한 뒤 사례형 부모 36개·98물음이고, 갱신 대상으로 남은 것은 **8개**다(모두 D등급 22·26·27·31·40·41·43·57번). 4번의 기준서형 2물음은 같은 정책으로 `pilot-16-008-standards-20260921`에 분리 보존했으므로, 기준서형이 섞여 있는 남은 세트는 40·41번 둘이다.
- (2026-09-21 갱신, r33~r40) D등급 8개(22·26·27·31·40·41·43·57번)를 처리한 뒤 사례형 부모 36개·102물음이고 **갱신 대상은 남지 않았다**. 40·41번의 기준서형 물음은 같은 정책으로 `pilot-18-005-standards-20260921`·`pilot-19-005-standards-20260921`에 분리 보존했으므로 기준서형이 섞인 세트는 없다.

## 2. 묶음을 고르는 기준

1. **한 회사의 사실 하나로 묶이는가.** 회사·역할·보고기간·통제 상태를 새 공통 사실에 맞출 수 있어야 한다. 전제가 충돌하면 한쪽을 고치고 계보에 남긴다.
2. **원출처가 같거나 요소가 이미 중복인가.** 같은 기출 요소에 연결된 세트, 서로의 요소를 재사용하는 세트를 합치면 중복이 사라진다.
3. **단계가 이어지는가.** 계획 → 수행 → 종결처럼 시간 순서로 배치할 수 있으면 물음 분할이 자연스럽다.
4. **같은 기준에서 결론이 갈리는 두 경우가 없는가.** 있으면 한쪽만 함정·옳지 않은 항목으로 남기고 다른 쪽은 삭제한다. 이 판단이 병합의 최대 제약이다.
5. **크기.** 2~3물음·7~12점이 기존 회차의 실적 범위다. 2물음·4~7점짜리 작은 세트를 우선 묶고, 이미 3물음·8~10점인 세트는 발문 형식만 바꿔도 종합문제 형태가 된다.

## 5. 병합 설계 체크리스트

- **항목 구성**: 옳은 절차·판단과 옳지 않은 절차·판단을 번호로 섞고, 물음마다 옳지 않은 것을 모두 고르게 한다. 옳지 않은 항목 수는 밝히지 않고 물음마다 다르게 둔다. 함정(틀려 보이나 기준상 허용되는 항목)이 옳다는 것도 원문으로 확정한다.
- **배점**: 물음마다 식별 1점 + 옳지 않은 항목마다 이유 또는 보완절차 1점. 구체적 후속절차 나열을 득점 요건으로 삼지 않는다. 한 항목에 독립된 잘못이 둘이면 점수를 늘리지 말고 항목을 나눈다.
- **정답 암시 금지**: 사실관계·발문·제목·태그가 결론·위반 사유·누락 절차를 알려 주지 않는다. 옳지 않은 항목에만 근거를 붙이거나 같은 근거를 되풀이하지 않는다.
- **대조되는 두 경우**: 원 세트들이 같은 기준에서 반대 결론을 정답으로 삼고 있는지 먼저 대조한다. 있으면 한쪽만 남기고 삭제한 요구를 계보에 적는다. r12·r13이 실제로 이 문제를 만났다.
- **전제 통일**: 회사·역할·보고기간·통제 상태·기록 방식을 하나로 맞추고, 바뀐 전제에서 승계한 항목의 옳고 그름이 여전히 성립하는지 근거 문단으로 재확정한다.
- **연도**: 20X1·20X2만 쓴다(대상 연도 2027년의 적용 판본은 `verification.notes`에 실제 연도로 기록).
- **출처**: 원 세트의 인용을 바이트·`content_hash` 그대로 재사용하는 것을 기본으로 하고, 새 인용은 등록된 공식 전문에서 발췌해 파일·행 범위를 남긴다.
- **중복 검토**: 이미 갱신된 세트와 요구가 겹치지 않는지 대조해 design의 중복 검토에 적는다. r13은 r12의 "자료 신뢰성" 요건과 갈라 두기 위해 인용 기준서를 달리했다.

3. 현재 정본 + 초안을 메모리에서 `validateAuthoringBank`로 검증하고 분류·카탈로그를 컴파일한다(정본 파일은 쓰지 않는다).
4. agent 내용 검토를 기록한다(`root-content-review-v*.json`). 미해결 발견사항이 남으면 게시하지 않는다.

## 7. 실행에서 걸렸던 것 (다음 회차 주의)

- **발문 바이트 중복**: `validateAuthoringBank`는 은행 전체에서 발문 문자열이 같으면 거절한다. "자료 N의 …" 같은 정형 발문은 다른 회차와 충돌하기 쉬우므로 단계 이름을 넣는다. r15가 이 문제로 v2를 다시 만들고 최종 발문으로 재실측했다.
- **criterion id**: 세트 안에서 고유해야 한다. 물음마다 같은 id를 쓰면 채점 모델이 잘못된 id를 돌려준다.
- **정본 해시 조율**: 후보 은행 빌드는 분류 카탈로그의 `source_file_sha256`과 정본 해시가 같아야 통과한다. 다른 세션이 정본을 설치하는 중이면 빌드를 미룬다.
- **승급과 커밋의 충돌**: pre-commit 전체 테스트가 실제 정본·장부 파일이 바뀌지 않는지 감시한다. 승급·설치가 도는 동안에는 커밋이 실패한다.
- **운영 명령**: 자동 모드 분류기가 릴리스 드라이버 실행을 막는다. `--prepare`·`--probe`·`--apply`는 사용자가 직접 실행하고, agent는 준비·기록만 맡는다.
- **기준 원문**: 다른 세션이 정본에만 설치한 변경이 있으면 정본이 운영 릴리스보다 앞선다. 증분 릴리스의 기준 원문은 활성 릴리스와 바이트가 같은 판본(예: HEAD 커밋의 정본)으로 잡고, 앞선 변경을 릴리스 범위에 포함할지 사용자에게 확인한다.
- **물음 수 상한 — 코드에서 직접 확인한다**: 실제 규칙은 `cpa_uploader/questionBankPublication.ts`의 `validateAuthoringBank`가 강제하는 "학습 유형·주제가 있는 물음은 **1~4개**, 기존 linked set은 세부 물음 **2~4개**"다. r29는 제작 지시가 "2~3"이라고 안내해 이미 3물음이던 갱신본에 물음을 더할 수 없다고 보고 3물음 안에서 단계를 재구획했고, 그 과정에서 KGA 706 문단 9(b)·9(c)가 빠졌다. 옛 코드 스냅샷이나 앞 회차 문서를 근거로 삼지 말고 **라이브 모듈을 직접 읽어** 확인한다(r31은 기준서형 분리본을 2물음 한 세트로 둘 수 있는지 이 방식으로 확인했다).
- **확장 회차는 대상 갱신본의 방식·전제를 정본에서 직접 읽는다**: 배정서나 설계 메모가 적은 전제가 실제 판본과 다를 수 있다. r31은 배정이 "대응수치 방식으로 고정"이었으나 대상 갱신본 `fact1`이 외부감사법에 따른 **비교재무제표** 방식이고 `verification.notes`도 KGA 710 문단 2를 들었으며, 항목의 근거 문단이 모두 비교재무제표 절이었다. 지시대로 했다면 갱신본 7점 가운데 다섯 항목이 근거를 잃는다. 확장 전에 정본의 사실관계·`verification.notes`·인용 문단을 직접 대조하고, 배정과 어긋나면 정본을 근거로 반박해 판단을 `lineage.json`에 적고 설치 전에 조율자가 확인한다.
- **기준서형 세트를 함께 추가할 때 — 2026-09-21에 해결**: r19까지의 드라이버는 새 세트의 학습 단위를 `<세트ID>--case`로만 찾았다. 기준서형은 물음마다 `<세트ID>--<물음ID>--standard`이므로 r16~r19에서는 apply가 커밋된 뒤 이 단정에서 멈춰 재개 스크립트(`verify-v1.mjs`)로 처리해야 했다. r20~r27 사본은 드라이버 바이트가 `preparation.json`의 `code_files`로 **고정되기 전에** 분류의 `question_style`을 읽어 유형별로 갈라지도록 고쳤고(사례형은 세트당 한 단위, 기준서형은 물음마다 `<세트ID>--<물음ID>--standard`와 `facts=[]`), 결과를 `roundtrip.json`의 `new_unit_checks`에 남겨 중단 없이 끝냈다. 드라이버 사본은 회차마다 새로 만들므로 **새 사본을 만들 때 이 유형별 확인을 유지한다**. 고정된 뒤에는 고칠 수 없으니 확인은 `--prepare` 전에 끝낸다.
- **지시서의 문단 번호는 등록 전문으로 확인한다**: r35 배정의 "문단 22·A81 계열"은 2025 개정 전문에서 문단 22(b)의 적용자료가 A109~A113이라 A81이 다른 절의 문단이었고, r39 지시의 "문단 25·26"(정상거래조건 주장의 증거·공시의 적정성)은 등록 전문에서 문단 24·23(a)(iii)였다. 두 회차 모두 등록 전문을 직접 읽어 바로잡았다. 옛 판본이나 기억의 문단 번호를 지시에 적으면 제작자가 없는 문단을 찾거나 다른 절의 문단을 쓰게 된다.
- **근거가 KGA가 아닌 세트**: r38의 근거는 분·반기재무제표 검토준칙이다. `validateAuthoringBank`는 `KGA ` 접두 page만 `classification.standards`와 대조하므로 이런 세트는 `standards`가 빈 배열이어야 하고 `### KGA NNN:` 구간 검사도 건너뛰어진다. 등록 원문에 있는 문단만 쓸 수 있으므로(r38은 여덟 문단), 배정 전에 등록 원문의 범위를 확인하고 부족하면 등록을 먼저 결정한다.
