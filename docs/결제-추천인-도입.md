# Audit Say 결제·추천인 도입

2026-09-13 로컬 구현 기록이다. CTA_tax_law의 현재 결제 코드와 동일한 정책을 적용하고, 결제·추천 보상·PRO 권한은 Audit Say의 `cpa_*` 데이터로 분리한다. 공통 계정·닉네임은 계속 공유한다.

무료·유료 기능 제한 확대 여부는 아직 확정되지 않아 기존 학습 횟수·오답노트 접근 정책을 유지한다. 요금제 화면도 이 상태를 명시한다.

## 정책과 구현

| 항목 | 적용 내용 |
| --- | --- |
| 이용료 | 9,900원, 결제마다 30일 연장 |
| 결제 방식 | 토스페이먼츠 자동결제 카드 등록 → 첫 결제 → 정기 갱신 |
| 추천인 | Audit Say에 가입한 회원의 공통 닉네임으로 확인, 자기 추천 불가 |
| 추천 자격 | 최초 결제 전에 한 번 등록, 서비스 탈퇴·재가입으로 초기화되지 않음 |
| 추천 보상 | 추천받은 회원의 첫 결제 성공 후 30일 경과 시 양쪽에 각 30일 지급 |
| 보상 지급 제외 | 첫 결제 취소·부분환불, 보상 확정 전 계정/서비스 비활성화 또는 가입 버전 변경 |
| 해지 | 다음 자동 갱신을 중단하고 남은 이용기간은 유지 |
| 결제 실패 | 확정 거절 시 1시간 → 12시간 → 24시간 재시도, 네 번째 실패 시 만료 |
| 응답 불명 | 원래 주문번호를 보존하고 결과를 확인하며, 확정 거절 횟수로 세지 않음 |
| 탈퇴 후 결제 도착 | 이용권을 복구하지 않고 결제 증거와 환불 검토 상태만 기록 |
| 관리자 PRO | 기존 PRO는 `manual_pro`로 보존. 유료기간과 별개로 관리하며 탈퇴 시 해제 |

`cpa_subscription`, `cpa_payment_log`, `cpa_referral`, `cpa_pro_reward`가 구독·결제·추천 관계·보상 원장이다. `cpa_billing_key_cleanup`은 카드 키 삭제 재시도, `cpa_verified_payment_cancellation`은 성공 원장보다 먼저 도착한 검증된 취소를 보관한다. `cpa_billing_payment_resolution_log`는 운영자가 공급자 거래 내역과 대조하여 미청구를 확정한 예외 조치의 근거다.

결제 승인 요청 전 DB가 회차와 주문번호를 선점하고, 성공 기록·이용기간 연장을 한 트랜잭션으로 처리한다. 주문번호와 성공 회차의 고유 제약이 중복 결제 기록을 차단하며, 추천 관계 상태 전환과 행 잠금이 보상 중복을 막는다. 앱·worker 모두 서비스 가입 버전을 확인하므로 이전 가입의 지연 응답이 재가입 후 권한을 바꾸지 않는다.

결제 원장은 회차 식별 기준 `billing_period_end`와 실제 이용기간이 더해진 시작점 `granted_period_start`를 따로 기록한다. 장기 만료 후 재구독·지연 갱신의 전액환불은 실제로 부여한 기간을 회수하고, 이미 남아 있던 유료기간·추천 보상은 보존한다. 미확정 주문이 있는 동안 추천 보상이 추가되어도 원래 주문번호·재시도 시각·실패 횟수를 유지하여 결과 확인이 계속되도록 한다.

회원은 자신의 결제 이력과 추천 정보를 조회할 수 있다. 빌링키·customerKey·선점 토큰은 서버에서만 읽고, 구독·보상 변경 RPC는 `service_role` 전용이다. 내부 기존 구현 함수는 `service_role`에서도 직접 호출할 수 없다.

전체 계정 삭제 시 구독·결제·추천·보상 행을 삭제하지 않고 회원 참조를 `NULL`로 바꾼다. 미확정 주문·카드 키 정리·환불 검토가 남으면 Auth 삭제를 막는다. 공통 탈퇴·계정 삭제 RPC는 두 서비스의 정리 상태를 함께 확인하며 기존 CTA 처리 경로는 유지한다.

Supabase의 기존 앱 환경변수는 그대로 필요하다. 공유 Supabase의 CTA용 `TOSS_SECRET_KEY`와 Vault `cta_*` 항목을 Audit Say 설정으로 덮어쓰지 않는다. Audit Say의 공개 키와 서버 키는 같은 자동결제 MID에 속해야 한다. 서버 키는 customerKey 생성에도 사용하므로 운영 도중 바꾸면 기존 카드의 재등록이 필요할 수 있다.

## 배포 순서

이 변경은 로컬 구현·검증까지 완료한 상태다. 운영 DB 적용, Edge Function 배포, 토스 운영 키 설정, 웹훅 등록과 실제 결제는 별도 실행해야 한다. 작업 시점의 로컬 환경에는 Audit Say 토스 키가 설정되어 있지 않았다.

1. 공통 계정 마이그레이션 `20260910090000_common_accounts.sql`이 적용된 공유 DB인지 확인하고, `20260913010000_cpa_billing.sql`을 먼저 적용한다. 기존 `manual_pro` 백필을 보존해야 하므로 적용 이력 없이 재실행하지 않는다.
2. Next.js에 Audit Say 전용 토스 키를 설정하고 `/pricing`, `/billing/success`, `/billing/fail`, `/api/webhooks/toss`가 배포 도메인에서 동작하도록 앱을 배포한다.
3. `process-cpa-billing`을 배포하고 Edge Function의 `CPA_TOSS_SECRET_KEY`를 설정한다. worker는 POST 요청과 service-role bearer를 자체 검증한다. 배포 시 JWT 게이트 설정은 운영 Supabase 키 형식과 맞춘다.
4. 토스 개발자센터에서 `PAYMENT_STATUS_CHANGED`, `BILLING_DELETED` 웹훅을 Audit Say 도메인의 `/api/webhooks/toss`로 등록한다. 앱은 웹훅 본문의 결제 상태만으로 권한을 바꾸지 않고 공급자 API로 재조회한다.
5. Vault의 `cpa_supabase_url`, `cpa_service_role_key`를 등록하고 `20260913010100_cpa_billing_schedule.sql`을 적용한다. 값 자체를 마이그레이션·저장소·실행 기록에 남기지 않는다.
6. 테스트 MID로 카드 등록, 첫 결제, 중복 콜백, 해지, 검증된 취소, 탈퇴 후 정리 경로를 확인한 뒤 운영 MID로 전환한다. 실제 청구와 환불은 이 로컬 검증에서 실행하지 않았다.

```bash
supabase functions deploy process-cpa-billing
```

잡 이름은 `cpa-monthly-billing`(매일 KST 01:00), `cpa-retry-billing`(30분마다), `cpa-downgrade-expired-pro`(매일 KST 01:05)이다. Vault 값이 없으면 호출 함수는 NOTICE를 남기고 건너뛴다. 적용 후 `cron.job`, `cron.job_run_details`, Edge Function 로그에서 호출과 오류를 확인한다.

미확정 결제를 공급자 404·네트워크 시간 초과만으로 실패 처리하지 않는다. 탈퇴한 주문에 실제 청구가 없었음을 운영자가 거래 원장으로 확인한 경우에만 DB 소유자 전용 `cpa_resolve_withdrawn_order_no_charge`에 확인 근거를 기록한다. 이 함수는 앱·worker의 일반 복구 경로에 노출하지 않는다.

## 검증 범위

```bash
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test tests/accountPolicy.test.ts tests/accountRoutes.test.ts tests/subscriptionEntitlement.test.ts tests/billingApi.test.ts tests/billingDatabase.test.ts tests/billingWorker.test.ts
npm run typecheck -- --incremental false
npm run build
```

격리 PGlite에서 실제 마이그레이션을 적용하여 두 서비스 권한 분리, 중복 성공 방지, 30일 추천 확정과 환불 제외, 가입 버전 검사, 비확정 주문 보존, 실패 재시도 소진, 수동 PRO 보존, 행/컬럼 권한, 탈퇴 중 늦은 결제·삭제 차단, 서비스 전용 RPC 권한과 최종 금융 원장 보존을 검증한다. 장기 만료 후 재구독·지연 갱신의 전액환불, 다른 결제와 추천 기간 보존, 미확정 주문 중 추천 보상 이후 재시도도 포함한다. worker 검증은 실제 코드를 공급자/Auth/RPC 대역과 실행하여 유효 가입만 새 청구가 가능하고 탈퇴·삭제 계정은 원래 주문을 조회하는지 확인한다.

운영 Supabase의 pg_cron·pg_net 실행, Edge 배포 런타임, 토스 결제창·실제 청구·실제 환불·운영 웹훅 전달은 로컬 테스트 범위에 포함하지 않는다.

계정·결제 API 통합 테스트 44개와 DB·worker 테스트 13개(총 57개), 전체 타입 검사, 변경 코드 ESLint, production 빌드를 통과했다. 브라우저에서 비회원 요금제, 인증 정보 없는 결제 콜백, 로그인 전 구독 관리 안내를 확인했다. 전체 `npm test`도 시도했지만 결제와 관계없는 기존 `questionV3Publication.test.ts`의 게시 CLI 검사가 장시간 실행되어 중단했으며 전체 테스트 통과로 기록하지 않는다. 추가 `noUnused` 검사는 기존 출제 draft 두 파일의 미사용 변수 때문에 실패했으며 해당 출제 파일은 이 작업에서 수정하지 않았다.
