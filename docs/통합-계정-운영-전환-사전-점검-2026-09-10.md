기존 계정을 초기화할 재무 미처리 차단 요인은 발견하지 못했다. 실제 변경 직전에 계정 UUID 집합과 재무 상태를 재검사해야 한다. 삭제는 새 마이그레이션으로 재무 FK 보존을 먼저 적용한 뒤, 공통 계정 종료 RPC가 준비 완료한 계정만 Supabase Auth Admin에서 삭제하는 순서다.

원래 cron은 4개 모두 활성 상태다. 기존 ID·명령 해시·일정을 매니페스트에 고정했다.

| ID | 이름 | UTC 일정 |
|---|---|---|
| 1 | monthly-billing | `0 16 * * *` |
| 2 | retry-billing | `*/30 * * * *` |
| 3 | downgrade-expired-pro | `5 16 * * *` |
| 4 | cpa-learning-guest-retention | `0 * * * *` |

Auth의 원래 `disable_signup=false`, `external_anonymous_users_enabled=true`를 별도로 저장했다. 전환 중에는 둘을 각각 true/false로 바꾸고 기존 앱 요청·cron을 중지한 뒤 고정 계정을 처리한다. 완료 후 이 가입 허용 값과 원래 cron 활성 상태만 복원한다.

운영 Auth 콜백 허용 목록에는 현재 세법 콜백만 있으며 감사 콜백 추가가 필요하다. 현재 최소 비밀번호 길이는 6으로 새 앱의 8자 기준에 맞춰야 한다. 루트 작업의 읽기 전용 Edge 점검에서 `process-billing`은 ACTIVE version 1, JWT 확인 활성이고 `TOSS_SECRET_KEY`는 등록되지 않은 것으로 확인했다. 기존 결제 비활성 설정을 유지하며 임의 키 설정이나 실제 청구를 하지 않는다.

전환 실행기는 `--apply` 없이는 읽기 전용 미리보기다. 정확한 프로젝트·매니페스트 SHA·SQL SHA·계정 집합·콘텐츠·기존 함수·cron 해시를 재검사한다. `migrate/reset`은 실제 가입 차단 설정과 cron 비활성, 명시적 유지보수 확인도 요구한다. 최신 매니페스트와 체크포인트는 로컬 `tmp/`에 보관하며, 계정 식별자가 있는 체크포인트는 출력·공개하지 않는다.

00:40 UTC 재점검에서도 채용 관련 테이블 4개·조회 뷰 1개·RPC 3개는 모두 없었다. 이번 계정 전환은 이 기존 상태를 유지한다. 채용 코드가 별도로 배포되어 있어도 채용 DB를 이번 작업에 추가 설치하지 않는다. 전환 실행기의 `assertSchema`는 해당 객체 존재 여부·기본 열·함수/뷰 정의를 고정하며, 새 cron 또는 채용 스키마가 동시에 생기면 변경 전에 중단한다. 채용 공고·게시판 테이블이 설치된 상태에서 준비하면 해당 콘텐츠 행 수도 보호 대상에 포함한다.

향후 `20260909010000_kicpa_jobs.sql`을 **공통 계정 마이그레이션 이후** 설치할 때는 구독자 테이블에 `membership_version bigint` 열과 `common_learning_membership` INSERT/UPDATE 트리거를 함께 설치하고 `public.common_guard_learning_membership()`을 호출해야 한다. 버전 열에는 INSERT 기본값을 두지 않으며, 기존 데이터가 있다면 현재 서비스 가입 회차로 검증·이관한다. 이 보강 없이 과거 채용 SQL만 나중에 적용하면 공통 마이그레이션의 조건부 가드가 소급 설치되지 않는다. 새 계정 코드의 구독 변경 요청은 버전 열이 없으면 실패하지만, 이를 운영 완료 상태로 간주해서는 안 된다. 새 환경에서 전체 마이그레이션을 순서대로 적용하면 채용 SQL 다음에 공통 계정 SQL이 가드를 설치한다. 향후 설치 시 구독 저장·탈퇴 삭제·이전 회차 요청 차단을 함께 검증한다.
