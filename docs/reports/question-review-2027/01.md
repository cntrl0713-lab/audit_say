# 주제 01 검토 결과 — 감사인의 책임과 품질관리

> 후속 결정(2026-09-08): [주제01–03 수정 결정](../../plans/question-review-01-03-remediation.md)을 따른다. 열거형 모두 작성·정수 배점·새 제출마다 경험치 전액 가산이 확정됐다. 본문의 실측·기대값은 당시 계약의 기록이며, 정책과 충돌하는 수정 제안·답변 대기 상태는 후속 결정으로 대체한다. 제품 수정 완료를 의미하지 않는다.

검토일: 2026-09-08(한국시간). 대상: **4세트·8물음·24개 criterion·24점**. 내부 검토 자료이며 정답과 합성 답안을 포함한다.

**전수 검토 기록은 완료했다. 2027년용 사용 적합 판정은 보류한다.** 채점에 영향을 주는 미해결 문제가 있고, 2027년 시험의 기준서 판본 지정은 별도 확인이 필요하다. 이번 작업은 검토·실측·수정안 작성이며 문제은행이나 제품 코드를 수정하지 않았다.

## 우선 수정할 문제

### 01-C01 · P1 · 한 문장의 독립 명제가 동일 인용이라는 이유로 감점됨

위치: [lib/questionV3.ts:276](../../../lib/questionV3.ts#L276), [lib/questionV3Grading.ts:264](../../../lib/questionV3Grading.ts#L264). 영향: 001/sub1 crit1·2, 002/sub1 crit2·3, 003/sub1 crit3·4·5 등 여러 주제.

답안 ‘업무팀의 유의적 판단과 결론을 감사보고서일 또는 그 전에 객관적으로 평가하도록 설계된 절차이다.’에는 평가 내용과 시점이 모두 있다. 두 criterion이 이 문장을 인용하는 모의 응답을 실제 채점 경로에 넣으면 기대 **2점 → 1점**이 된다. 인용 문자열만으로 독립 명제를 동일 사실로 취급하기 때문이다. 같은 답안의 실모델 호출에서는 인용을 나누어 2점이었으므로 실제 평가에서 항상 감점된다는 뜻은 아니다.

수정안: 동일 문자열만으로 다른 criterion을 0점으로 만드는 처리를 제거하고, 동일 사실의 반복 득점은 requirement/명제의 중복 여부로 관리한다. 프롬프트도 ‘동일 quote 금지’ 대신 독립 명제에 동일 문장이 근거가 될 수 있음을 허용하고 정확한 인용을 요구한다. 독립 명제 2점과 반복한 상장기업 사실 1점의 두 사례를 함께 회귀 검증한다. 단순히 인용 문자열을 조금씩 다르게 만드는 방식으로 해결하지 않는다.

### 01-C02 · P1 · 4개 이후의 열거 답안을 채점함

위치: [lib/questionV3Grading.ts:237](../../../lib/questionV3Grading.ts#L237), [lib/questionV3.ts:296](../../../lib/questionV3.ts#L296). 대상: 003/sub1 crit6 및 모든 `ignore_after_limit` 물음.

003/sub1은 `max_entries=4`, `overflow_policy=ignore_after_limit`이다. 무관한 문장을 1번, 올바른 네 항목을 2–5번으로 제출했다. 기대는 마지막 실행 여부 criterion을 제외한 **5점**이다. 실제 세 번 모두 5번째 항목의 crit6에 1점을 부여했다. 총점은 **5/6/6점**이었다. 첫 실행의 5점은 crit4의 잘못된 인용으로 1점이 상쇄된 결과이므로 통과가 아니다.

수정안: 번호·줄바꿈 등 열거 항목의 경계를 명시하고, 코드가 계약상 허용되는 항목만 모델에 전달하며 인용 검증도 그 범위에서 수행하도록 한다. `constraints`를 프롬프트에 추가하는 것만으로 끝내지 않는다. 이 물음의 네 항목과 여섯 criterion은 모순이 아니다. 세 번째 항목의 성격·범위·결론을 각각 평가하므로 항목 수와 criterion 수를 구별해야 한다. UI에도 초과 항목 처리 안내를 표시한다.

### 01-D01 · P1 · 결론 생략 답안의 판단 점수가 일관되지 않음

대상: 004/sub1 crit1·2. `claim`은 자체 판단만으로 처리하는 것은 부적절하다는 결론과 회계법인 커뮤니케이션을 함께 요구하지만, `critical_facts`는 커뮤니케이션 필요만 표시한다.

‘회계법인과 업무수행이사가 필요한 조치를 취할 수 있도록 신속히 커뮤니케이션해야 한다.’만 쓰고 부적절하다는 결론을 생략한 경우, crit1이 **met/not_met/met**으로 바뀌었다. 해당 물음 점수는 **2/1/2점**이다. 최초 사전 기대값은 현행 claim의 두 요구를 모두 명시해야 한다는 해석에서 1점이었다. 이후 사용자가 **‘요구 조치에서 결론이 분명하면 인정’**으로 확정했다. 확정 정책상 기대는 2점이며 두 번째 실행의 1점이 부당한 감점이다. 최초 판정 기록은 보존하고 [확정 정책에 따른 재판정](grading-cases/01-live-policy-reassessment.json)을 별도 작성했다.

수정안: crit1을 ‘회계법인에 해당 정보를 커뮤니케이션해야 함을 제시하여 자체 판단만으로 처리할 수 없음을 명시하거나 분명히 함’으로 정리하고 `critical_facts`에도 함축된 결론을 인정하는 동일한 계약을 반영한다. crit2의 목적·신속성 요구와 총 2점, partial 금지는 유지한다. 발문에 ‘요구되는 조치를 통해 판단이 분명히 드러나는 답안도 인정한다’는 안내를 추가한다. 이 정책은 확정됐으며 이번 검토에서는 수정안으로 기록했다.

### 01-C03 · P2 · 화면과 서버의 입력 한도가 다름

위치: [QuizClient.tsx:212](../../../app/quiz/QuizClient.tsx#L212), [lib/questionV3.ts:156](../../../lib/questionV3.ts#L156), [app/actions.ts:60](../../../app/actions.ts#L60). 전체 물음에 영향.

화면은 20,000자까지 허용하지만 서버는 5,000자를 초과하면 거절한다. 5,001자 합성 입력으로 실제 서버 액션의 검증 분기를 격리 실행하여 거절을 확인했다. 수정안: 공통 한도 상수를 만들어 화면·payload 검증·채점 함수에 동일하게 사용하고 제한을 사용자에게 표시한다. 5,000자를 유지한다면 화면도 5,000자로 맞춘다.

### 01-C04 · P2 · 채점 성공 후 프로필 갱신 실패가 채점 실패 화면으로 처리됨

위치: [QuizClient.tsx:63](../../../app/quiz/QuizClient.tsx#L63). 전체 세트에 영향.

정상 결과를 받은 뒤 `refreshProfile`이 실패하면 catch에서 `solving`으로 되돌린다. 4세트·두 화면 폭에서 재현했다. 사용자가 재제출하면 모델 호출과 진도 반영을 반복할 수 있다. 수정안: 채점 결과를 유지하고 프로필 갱신 실패는 별도 재시도 안내로 처리한다.

### 01-C05 · P2 · 보안 감점의 원인을 결과 화면에서 알 수 없음

위치: [lib/questionV3Grading.ts:110](../../../lib/questionV3Grading.ts#L110), [QuizClient.tsx:271](../../../app/quiz/QuizClient.tsx#L271).

개별 물음의 보안 플래그는 해당 물음만 0점으로 만드는 데에는 정상 반영된다. 그러나 반환되는 `security_flag`는 전역값뿐이며, UI는 그 전역값도 표시하지 않고 criterion의 `reason`도 표시하지 않는다. 정상 오답과 보안 감점을 구별하기 어렵다. 수정안: 개별 물음의 보안 상태와 사용자용 사유를 결과 계약에 포함하고 화면에 표시한다. 인용 검증으로 감점한 사유도 보여준다. 내부 지시·비공개 출처는 표시하지 않는다.

### 01-D02 · P2 · 업무팀 배정의 첫 정답을 뒷받침하는 인용이 누락됨

대상: 004/sub2 crit3, req2, src2. 현재 source_quote는 **220 문단 14(b)만** 포함한다. 첫 정답인 기준·법규에 따른 수행 적격성·역량은 문단 14 본문과 (a)가 필요하다. 공식 PDF 57쪽과 로컬 본문의 문단 14에는 근거가 존재하므로 정답 자체가 허구인 것은 아니다.

수정안: src2와 req2의 인용을 문단 14 본문 및 (a)·(b) 전체로 확장하고 `source_span`과 공식 판본·쪽을 명시한다. 발문도 ‘업무팀과 업무팀원이 아닌 감사인측 전문가들이 총체적으로 갖추어야 할 적격성과 역량을 평가할 때, 업무수행이사가 확인해야 하는 두 가지 수행능력을 제시하시오.’로 명확히 한다. 사람마다 모든 능력을 요구하는 것으로 오해하지 않게 한다.

### 01-D03 · P2 · 요구하지 않은 순서와 불완전한 검증 메타데이터

대상: 004/sub2의 `constraints.ordered=true`, 004의 source_refs.content_hash·verification.

문단 14와 발문에 답안 순서 요구가 없다. 역순 답안은 실제 2점이었다. `ordered`는 현재 프롬프트에 전달되지 않아 실행되지 않지만, 그대로 구현하면 부당한 감점이 생긴다. `ordered=false`로 바꾸는 수정안을 제안한다. `max_entries=2`, `overflow_policy=none`은 이번 검토만으로 새 초과 감점 규칙을 추가하지 않는다.

004의 해시는 `h-01-004-src1/2`라는 자리표시자이며 상태는 published/verified인데 메모에는 ‘게시 전 사람 의미 검수 필요’가 남아 있다. 실제 검토 상태와 검증 메타데이터를 일치시키고 인용의 실제 해시를 기록해야 한다. 검증기가 현재 이를 통과시켰다는 사실은 의미 검수 완료의 증거가 아니다.

## 미검증·정책 확인 및 후속 수정 순서

1. 004/sub1은 **요구 조치에서 결론이 분명하면 인정**하는 정책으로 확정됐다. **동일 세트 반복 풀이의 경험치 정책**은 질문에 대한 답변 대기다. 현재 반복 제출은 매번 양수 점수를 `incrementProgress`에 전달한다.
2. 수정 순서는 확정된 D01 계약 반영 → D02/D03·E01 데이터 정합성 → C01/C02 공통 채점 → C03–C05 화면·결과 전달이다. 공통 변경은 19개 주제에 영향이 있을 수 있으므로 이 주제만 통과시키고 끝내지 않는다.
3. 진도 저장이 false를 반환해도 서버 액션은 성공 결과를 돌려준다. 실제 액션을 격리하여 확인했다. DB 저장 실패의 표시와 반복 정책, 원자적 가산은 후속 연동 수정에서 함께 다룬다. 실제 운영 DB 동시성·권한·RPC·로그인은 이번에 실행하지 않았다.
4. 서비스의 최대 45초 × 3회 재시도 설정과 라우트 `maxDuration=60`의 조합은 배포 환경에서 확인이 필요하다. 이번 실제 API 평가에는 전송 오류가 없었고 이 시간 초과 경로를 운영 환경에서 실측하지 않았다.
5. 실제 모델의 동일 인용·부정·누락·열거·모범답안 사례는 평가했다. 보안 플래그 강제 처리와 비허용 partial은 코드 모의 검증이며 모델의 보안 탐지 민감도·오탐률 전수 평가로 확대 해석하지 않는다.
