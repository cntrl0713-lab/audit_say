# 채점기 id 오반환 결함 해결과 신규 세트 재검수

작업일: 2026-09-10 ~ 2026-09-11. 수행: Claude(Opus 5), 소유자(JUNYEONG) 지시.

대상은 2026-09-10 신규 배치(`cpa_uploader/drafts/frequency-gap-2026-09-10/`)의 게시 8세트와 보류 1세트(pilot-05-008), 그리고 공통 채점 코드다. 운영 DB 반영(5단계)은 이 보고서의 범위가 아니다.

## 요약

- **원인:** 채점 응답의 id 칸이 아무 문자열이나 허용했고, 프롬프트 출력 예시가 `q1`, `q1.c1`을 보여 줬다. 모델이 이 예시를 따라 쓰면 응답 전체가 검증에서 거부되었다. pilot-05-008은 이 오류가 반복되어 게시를 보류했었다.
- **해결:** 응답 스키마가 세트의 실제 물음·criterion id만 고르도록 제한했다. 같은 조건에서 수정 전 20회 중 5회였던 실패가 수정 후 0회가 되었다.
- **재검수:** 채점 코드가 바뀌어 게시 8세트의 실제 채점 사례를 다시 실행했다. 이 과정에서 사례 판정의 흔들림과 새 채점기의 경향 두 가지가 드러났다. 사례 문구 교체와 채점 기준 1건 수정 후 9세트 모두 전건 일치했다.
  - 8세트는 승급 장부에 재검수·재게시로 기록했다.
  - pilot-05-008은 새 채점기에서 두 번 연속 51/51로 통과해 게시 준비를 마쳤다.
- **남은 일:** 운영 DB는 아직 2026-09-10 릴리스다. 새 채점기 배포와 문제은행 이관(pilot-13-006 수정, pilot-05-008 게시)을 함께 해야 한다.

## 1단계: 현재 실패율 측정

| 구분 | 내용 |
| --- | --- |
| 원인 | pilot-05-008에서 채점 모델이 물음 id를 `q1`로 반환해 채점 전체가 실패했다. 공통 사실의 "물음 1은…" 안내문을 지우기 전 6회 중 2회, 지운 뒤 채점 사례 실행 중 1회 발생했다. |
| 목적 | 수정 전후를 비교할 기준 실패율을 잰다. |
| 방법 | 수정 전 채점기로 모범답안 10회와 채점 사례 답안 50종을 각 1회 채점했다(60회 호출). |
| 결과 | 예외 0회. 모범답안은 10회 모두 12/12점이었다. 드문 실패라 기준 측정만으로는 재현되지 않았다. |

재현을 위해 예전에 실패하던 조건, 곧 공통 사실에 안내문이 있는 복사본으로 모범답안을 20회 채점했다. 수정 전 채점기는 **20회 중 5회 실패**했고, 5회 모두 `q1`/`q1.c1…`/`q2.c5`처럼 예시의 id 체계를 통째로 따라 썼다.

## 2단계: 채점기 수정

| 구분 | 내용 |
| --- | --- |
| 원인 | `buildGradingResponseSchema()`가 `subquestion_id`·`criterion_id`를 자유 문자열로 두었다. 출력 예시는 세트와 무관한 `q1`, `q1.c1`이었다. 틀린 id가 오면 `validateJudgmentCoverage`가 채점 전체를 거부한다. |
| 목적 | 모델이 틀린 id를 만들 수 없게 한다. 틀린 id를 짐작으로 고치면 판정이 다른 물음에 붙어 점수가 조용히 틀릴 수 있어 그 방식은 쓰지 않는다. |

바꾼 것:

- `lib/questionV3Grading.ts`
  - 응답 스키마를 세트별로 만든다. 물음마다 `anyOf` 변형 하나를 두고, `subquestion_id`는 그 물음 id 하나만, `criterion_id`는 그 물음의 criterion id만 enum으로 허용한다.
  - 엄격 모드 구조화 출력이라 스키마에 없는 id는 생성 단계에서 만들어지지 않는다.
  - 출력 예시는 해당 세트의 첫 물음·criterion id를 쓴다.
- `lib/ai/openaiStructured.ts`: 응답이 중간에 끊기면 오류 메시지에 이유(`incomplete_details.reason`)가 남는다.
- 테스트 3건 추가: 스키마의 id 제한, 예시에 `q1`이 없음, 끊긴 이유 표시.
- 출력 토큰 한도(8,000)는 올리지 않았다. 측정에서 응답은 최대 약 1,000토큰이었다.

## 3단계: 수정 후 재측정

| 측정 | 채점기 | 호출 | 실패 |
| --- | --- | ---: | ---: |
| 안내문 있는 복사본 | 수정 전 | 20 | 5 |
| 안내문 있는 복사본 | 수정 후 | 20 | 0 |
| 현재 세트 전체 | 수정 후 | 60 | 0 |

- **결과:** id 실패가 사라졌다. 모범답안은 매회 만점이었다.
- **새로 드러난 것 (id와 무관):**
  - "…만 통보한다" 같은 조건 경계 사례 8건에서 채점기는 contradicted, 기대값은 not_met이었다. 둘 다 0점이다.
  - 동의 표현 1건은 실행마다 met과 not_met이 바뀌었다.
  - 이 문제는 4단계에서 처리했다.

## 4단계: 게시 8세트 재검수와 pilot-05-008 검수

### 원인과 목적

| 원인 | 내용 |
| --- | --- |
| 채점 코드 변경 | 기존 승급 장부의 채점 기록은 채점 코드 해시에 묶여 있다. 채점기를 바꾸면 새 채점기로 사례를 다시 돌려야 한다. |
| 은행 기준 불일치 | 원 의미검수 receipt는 pilot-05-008 초안이 은행에 있던 중간 상태에 묶여 있었다. 그래서 현재 104세트 은행 기준으로 같은 검수 내용을 다시 확정했다. 검수 단위·사례·근거가 원 검수와 같은 것을 대조해 확인했다. |

목적은 두 가지다. 게시 8세트가 바뀐 채점기에서도 기대대로 채점되는지 실제 모델로 확인해 장부에 남기고, pilot-05-008을 게시 가능한 상태로 만든다.

### 발견 1: 한 번의 전건 일치는 운일 수 있다

첫 재채점에서 게시 8세트의 채점 실행 234회 중 5개 세트 7건이 어긋났다. 이전에 1회 실행으로 전건 일치했던 세트들이다. pilot-05-008은 두 번의 실행에서 매번 다른 사례 1건씩이 어긋났다. 어긋난 사례를 수정 전·후 채점기로 각 6회 반복했다.

| 사례 | 수정 전 채점기 | 수정 후 채점기 |
| --- | --- | --- |
| 05-007 crit3 조건 경계 | contradicted 5 / not_met 1 | 같음 |
| 13-007 crit7 조건 경계 | 3 / 3 | 4 / 2 |
| 16-009 crit7 조건 경계 | 3 / 3 | 3 / 3 |
| 16-008 crit1 조건 경계 | contradicted 6 | 3 / 3 |
| 13-006 crit8 조건 경계 | not_met 6 | not_met 5 / met 1 |

- 대부분은 수정 전부터 있던 흔들림이고, 조건 경계 사례의 not_met과 contradicted 사이(둘 다 0점)에 몰려 있다.
- **소유자 결정:** 조건 경계 사례는 두 0점 판정 중 어느 쪽이 나와도 일치로 본다(`cpa_uploader/questionReviewGrading.ts`, 테스트 1건, `cpa_uploader/README.md`). 반대 서술 사례는 여전히 contradicted여야 한다.

### 발견 2: 모호한 사례 문구

점수가 갈리거나 판정이 흔들린 사례는 6~10회 반복 실측으로 판정이 일정한 문장을 확인한 뒤 교체했다. 모델 결과에 맞춰 기대값만 바꾼 것이 아니다. 문구의 모호함을 근거로 교체했고, 근거는 `release/manual-review-notes.json`의 `case_overrides`에 있다.

| 사례 | 문제 | 교체 전 | 교체 후 |
| --- | --- | --- | --- |
| 13-006 crit8 조건 경계 | 절차 명칭만 적어 조건 경계가 모호 | met 5 / not_met 5 | contradicted 10/10 |
| 16-009 crit2 동의 표현 | "보고서일"이 감사보고서일인지 모호 | 23회 중 not_met 1 | met 10/10 |
| 05-008 crit3 조건 경계 | "사실만 알린다"가 누락·반대 사이에서 갈림 | contradicted 5 / not_met 3 | not_met 8/8 |
| 05-008 crit10 동의 표현 | "지배 부문"이 통제하의 부문과 뜻이 다름 | 13회 중 not_met 1 | met 10/10 |
| 05-008 crit11 동의 표현 | "총"이 빠져 대상이 모호 | 실행마다 달라짐 | met 6/6 |

pilot-05-008의 "…만"/"사소한"/"수행자별로" 조건 경계 7건은 명제의 나머지를 명시적으로 배제·대체한다. 측정 2회, 검수 1회, 반복 6회 모두 contradicted였고 16-008·16-009 선례와 같아 기대값을 contradicted로 정정했다.

### 중단과 재개

재채점 도중 다른 세션이 채점기를 다시 설계했다. 인용을 id로 고르는 방식(`lib/questionV3Evidence.ts`)과 별도 보안 판정 단계가 들어갔고, 채점 코드 해시 대상 파일도 늘었다. 이미 기록된 receipt에는 현재 채점 코드 해시를 요구하지 않도록 바뀌었다. 진행 중이던 채점 결과가 무효가 되어 승급하지 않고 멈췄다. 그 세션이 끝난 뒤 최종 채점기(해시 `61459102a538…`)로 다시 실행했다.

### 발견 3: 최종 채점기의 경향

최종 채점기로 9세트 중 7세트가 첫 실행에서 전건 일치했다. 어긋난 2건은 8회 반복해 보니 일시적 흔들림이 아니라 채점기의 일정한 경향이었다.

| 사례 | 최종 채점기 | 수정 전 채점기 | 조치 |
| --- | --- | --- | --- |
| 13-006 crit5: 발문이 요구하는 조건을 빠뜨린 답안(기대 not_met) | met 8/8 | not_met 6 / met 2 | 채점 기준 수정 |
| 13-008 crit2: 명시적 부정이 없는 반대 서술(기대 contradicted) | not_met 8/8 | contradicted 3 / not_met 5 | 사례를 명시적 부정으로 교체 |

- **13-006 채점 기준 수정 (게시된 문항 변경):** sub2 crit5의 명제와 핵심 사실에 "'입수할 수 있는 경우'라는 조건 없이 보고서 입수만 제시하면 충족하지 않는다."를 추가했다(KGA 402.12(a)의 "입수가능한 경우"와 대조).
  - 추가 후 조건 누락 답안은 not_met 8/8, 모범답안과 동의 표현은 met 각 8/8이었다.
  - 이 수정은 편집 정본에서 했다. 초안·작성 스크립트·렌더 문서는 제작 당시 기록으로 두었다.
- **13-008 사례 교체:** "…감사범위의 제한에 해당하지 않는다"로 바꾸어 contradicted 8/8이 나왔다. 문항 내용은 바꾸지 않았다.

## 남은 일과 위험

1. **운영 DB 미반영:** 운영은 2026-09-10 릴리스(`f5e24288-…`)다. 13-006 수정과 05-008이 아직 반영되지 않았다. 새 채점기만 먼저 배포하면 운영의 13-006에서 조건을 빠뜨린 답안도 점수를 받는다. 채점기 배포와 문제은행 이관을 함께 해야 한다.
2. **다른 게시 세트의 조건 처리:** 최종 채점기가 명제 안에 묻힌 조건을 느슨하게 보는 경향이 나머지 96세트에도 있을 수 있다. 배포 전 점검을 별도 작업으로 진행 중이다.
3. **coverage 연결 stale:** 13-006 수정으로 `frequency-gap-2026-09-10-A-2`가 stale로 표시된다. 연결 자체가 검토 전(`needs_review`)이라 의미를 다시 대조할 때 갱신한다. 해시만 새로 바꾸지 않았다.
4. **검수자:** 사람이 아닌 Claude가 소유자 지시로 대리 검수했다. 장부 근거에 그렇게 적었다.
5. **커밋 전:** 모든 변경은 커밋되지 않았고, 다른 세션의 변경과 같은 작업 트리에 있다.
