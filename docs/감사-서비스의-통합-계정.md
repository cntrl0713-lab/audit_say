# 감사 서비스의 통합 계정

2026-09-10 구현·배포 완료. 운영 DB·Auth 설정·두 앱과 결제 worker 배포·기존 계정 910개 삭제를 마쳤다. 현재 상태와 검증 근거는 [운영 전환 결과](통합-계정-운영-전환-완료-2026-09-10.md)를 참고한다.

공통·서비스별 관리 범위와 확정한 선택은 [통합 계정 운영 정책](auditsay-CTAtaxlaw-통합-계정-운영안.md)에 기록했다.

## 구현한 운영 방식

Supabase Auth UUID·이메일·비밀번호와 `common_profiles`의 닉네임·계정 상태를 공유한다. 감사의 가입·관리자·이용권·학습 기록·알림은 `cpa_users`와 기존 감사 테이블에서 관리한다. 별도 인증 서버나 통합 포털을 추가하지 않는다.

- `/`: 이메일 또는 공통 닉네임으로 로그인한다. 닉네임에서 이메일을 찾는 과정은 서버 내부에서만 처리한다.
- `/account`: 공통 닉네임·이메일·비밀번호, 감사 최초 가입·재가입·탈퇴, 통합 계정 삭제를 관리한다.
- `/account/recovery` → 인증 메일 → `/auth/callback` → `/auth/reset-password`: PKCE 교환이 확인한 복구 세션에만 사용자·세션에 묶인 10분짜리 서명 쿠키를 발급한다. 링크를 요청한 브라우저에서 연다.
- `/admin`: 감사 이용권과 감사 관리자 권한을 별도 항목으로 변경한다. 세법 관리자 권한은 변경하지 않는다.

로그인은 공통 계정 확인까지만 수행한다. 감사 미가입자는 이용 시작을 직접 확인하며, 탈퇴한 사용자는 재가입 안내에 동의해야 한다. 프로필 조회 실패·탈퇴·잠금을 일반 회원으로 처리하지 않는다. 비회원 체험은 기존 익명 세션만 사용한다.

공통 닉네임은 한글 완성형·영문·숫자 2~12자이며 대소문자 구분 없이 중복을 막는다. 새 비밀번호는 8~128자이고 기존 비밀번호의 로그인·본인 확인에는 새 최소 길이를 소급 적용하지 않는다. 공통 닉네임 변경은 다른 사이트의 다음 프로필 조회에도 반영된다.

이메일·비밀번호 변경, 서비스 탈퇴, 계정 삭제는 현재 비밀번호로 같은 UUID인지 다시 확인한다. 검증된 메일 복구만 현재 비밀번호 확인을 대신할 수 있다. 삭제 처리 중에도 복구 후 계정 삭제를 재시도할 수 있으며, 잠금 상태에서의 변경과 서비스 이용은 차단한다.

## 학습·탈퇴와 지연 작업

감사 서비스 탈퇴는 답안·채점·오답노트·경험치·알림 설정과 감사 이용권을 정리한다. 재가입은 같은 UUID의 새 가입 회차로 시작한다. 학습 제출 서명, 채점 RPC, 오답노트 변경, 채용 알림 설정에 회차 검사를 적용하여 이전 작업이 새 기록을 만들지 못하게 한다. 서버는 요청자의 공통 계정과 감사 가입 상태를 확인한다.

통합 계정 삭제는 DB가 두 서비스 종료와 결제 후처리 완료를 명시적으로 확인한 다음 Auth를 삭제한다. 처리 중에는 완료로 표시하지 않으며 계정 화면에서 다시 확인할 수 있다. 거래 증빙·환불 판정·최소 운영 기록은 별도 정책에 따른다. 세법의 미확정 결제는 [공유 DB 전환 문서](공통-계정-DB-구현-및-전환.md)의 절차를 따른다.

## 운영 전환

1. 공유 DB의 실제 스키마를 읽기 전용으로 확인한다. `node scripts/shared-account-preflight.mjs`는 `.env.local`의 관리 토큰으로 스키마 메타데이터와 공개 가능한 Auth 설정만 `tmp`에 저장한다. 사용자 행과 자격 증명은 출력하지 않는다.
2. 두 앱의 `NEXT_PUBLIC_SITE_URL`을 각 정규 HTTPS 주소로 설정한다. Supabase Auth 허용 목록에 양쪽 `/auth/callback`을 등록한다. 확인한 배포 주소는 `https://audit-say.vercel.app`와 `https://cta-tax-law.vercel.app`이며, 전환 직전 실제 정규 주소를 다시 확인한다.
3. 운영 전환에서 양쪽 콜백을 등록하고 Auth `password_min_length`를 6→8로 변경했다. 이메일 인증과 안전한 이메일 변경 설정은 유지했다.
4. 구버전 앱·결제 worker의 쓰기를 중단하고 공유 마이그레이션 `20260910090000_common_accounts.sql`을 한 번 적용한다. 양쪽 앱과 CTA 결제 worker를 함께 전환한다. 두 저장소의 서로 다른 과거 이력에 대해 무조건 `db push`하지 않는다.
5. 기존 계정 초기화는 마이그레이션과 별도 실행기로 완료했다. 이메일이 확인된 임시 검증 계정으로 양쪽 로그인·첫 가입·공통 닉네임·서비스별 권한·탈퇴·재가입·전체 삭제를 확인했다. 실제 이메일 발송과 카드 결제는 수행하지 않았다.

구버전 앱은 가입 회차를 전달하지 않아 쓰기가 거절되므로 이전 배포본으로 단독 롤백하지 않는다. 이번 감사 배포는 당시 운영에 이미 있던 채용·회계법인 코드도 보존했다.

## 검증

`npm run typecheck`, `npm run lint`, `npm run build`와 계정 정책·실제 API 경계·학습 DB·채용 알림 회귀 검사를 실행한다. `tests/sharedAccountsDatabase.test.ts`는 기존 양쪽 SQL 위에 새 마이그레이션을 적용하여 권한·탈퇴·결제·재가입 경계를 검증한다. 오프라인 검사는 실제 회원·메일·결제를 만들지 않는다.

전체 `npm test`에서 기존 `tests/questionV3Generation.test.ts:62` 한 건의 Windows CRLF 결함을 확인했다. 변경하지 않은 생성기의 LF 전용 정규식이 가이드의 템플릿 문구를 제거하지 못한다. 원본에서 반복 재현했고, 파일 변경 없이 해당 가이드를 메모리에서 LF로 읽으면 같은 테스트가 통과한다. 통합 계정 수정과 별개이며 문제 콘텐츠·생성기는 이번 작업에서 변경하지 않았다.

배포 전 전체 363건 중 362건 통과·위 기존 결함 1건 실패였다. 계정·학습·알림 집중 검사 48건과 공유 DB 검사 8건은 모두 통과했고, 두 서비스의 프로덕션 빌드와 타입·린트 검사도 통과했다. 세법은 전체 오프라인 검증과 추가 인증·결제 worker 회귀 검사도 통과했다. 로컬 브라우저에서 양쪽 로그인·가입 폼, 감사 계정 관리의 미로그인 차단·복구 화면과 비밀번호 입력 제한을 확인했다. 이후 운영 DB 적용 후 실제 로그인·가입·탈퇴 검증도 완료했다. 운영 이메일 전달과 실결제는 실행하지 않았다.
