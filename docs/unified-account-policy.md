# audit_say · CTA_tax_law 통합 계정 운영안

작성일: 2026-09-10. 이 문서는 운영 설계이며 코드·운영 DB 변경이나 계정 삭제를 실행하지 않는다.

## 1. 목적과 사용자 확정 사항

두 서비스의 이용자는 거의 겹치지 않는다. 통합의 목적은 하나의 계정으로 두 서비스를 이용하고, 로그인·계정 복구·계정 정보를 일관되게 관리하는 것이다. 상품·학습·서비스 운영은 독립적으로 유지한다.

- 같은 Supabase Auth의 회원 UUID 하나를 통합 회원 ID로 사용한다.
- 이용권은 서비스별로 판매·관리한다. 통합 이용권·공용 포인트·교차 판매 기능은 이번 범위에 넣지 않는다.
- 닉네임은 두 서비스에서 항상 동일하게 사용한다. 서비스별 닉네임 덮어쓰기는 허용하지 않는다.
- 두 서비스 모두 이메일 또는 공통 닉네임과 비밀번호로 로그인한다.
- 한 서비스에서 탈퇴하면 그 서비스의 개인 학습 기록을 삭제한다. 서비스 재가입 시 학습은 새로 시작한다.
- 서비스 탈퇴 시 해당 서비스 이용권도 종료한다. 남은 유료 기간은 재가입 시 복원하지 않고, 환불은 별도의 환불 정책에 따라 처리한다.
- 기존 계정을 보존하거나 병합할 필요는 없다. 기존 계정 초기화는 구현·전환 단계의 별도 작업이다.
- 자동 로그인 상태 공유(SSO)는 이번 범위에 포함하지 않는다. 사이트별 로그인에 같은 계정을 사용한다.

## 2. 공통으로 관리할 항목

| 항목 | 운영 규칙 |
|---|---|
| 회원 ID | 변경하지 않는 Auth UUID 하나. 닉네임·이메일 변경으로 ID가 바뀌지 않는다. |
| 이메일·비밀번호 | Supabase Auth를 정본으로 사용한다. 서비스 테이블의 이메일 복사본을 로그인 판정의 정본으로 사용하지 않는다. |
| 이메일 인증·계정 복구 | 두 서비스에 동일한 인증·변경·복구 규칙을 적용한다. 이메일 인증 후 정식 서비스 가입을 완료한다. |
| 닉네임 | 공통 프로필에 한 번 저장하고 두 서비스가 같은 값을 표시한다. 대소문자를 구분하지 않는 전역 중복 금지 규칙을 사용한다. |
| 닉네임 변경 | 공통 계정 설정에서 변경한다. 다른 서비스에도 반영된다는 안내를 제공하고, 각 서비스의 현재 프로필·랭킹에 반영한다. |
| 계정 상태 | 정상·보안 잠금·삭제 처리 중 상태를 공통 관리한다. 계정 탈취나 공통 인증 악용은 계정 전체 제한 대상이다. |
| 보안 알림 | 이메일·비밀번호 변경, 계정 복구 등 계정 관련 알림은 공통 관리한다. |
| 통합 계정 삭제 | 두 서비스의 종료 처리를 확인한 뒤 공통 계정을 삭제한다. 서비스 탈퇴와 별도 메뉴로 제공한다. |

통합 닉네임은 공개 표시 이름이며 내부 데이터 연결 키는 UUID이다. 다른 서비스 가입 여부·학습 기록·공통 UUID를 공개 프로필에 자동 노출하지 않는다. 향후 익명 후기 기능을 도입하면 별도의 익명 표시 정책을 적용한다.

## 4. 회원 상태·이용권·관리자 권한의 분리

현재의 `GUEST / MEMBER / PRO / ADMIN` 또는 `guest / member / pro / admin` 단일 등급을 운영상의 최종 기준으로 사용하지 않는다. 다음 세 가지를 독립적으로 판정한다.

| 축 | 예시 |
|---|---|
| 서비스 이용 상태 | 이용 중 / 이용 제한 / 탈퇴 처리 중 / 탈퇴 |
| 이용권 | 기본 이용 / 유료 이용권 및 만료일 |
| 관리 권한 | 일반 사용자 / 해당 서비스 관리자 |

- 유료 이용권을 구매해도 관리자 권한은 생기지 않는다.
- 관리자로 지정해도 다른 서비스의 권한이나 유료 구매 이력을 만들지 않는다.
- 프로필이 없거나 조회에 실패했다는 이유로 정식 회원 권한을 부여하지 않는다.
- 통합 계정 상태와 해당 서비스 이용 상태를 서버에서 확인한 후 기능 접근을 허용한다. 유료 기능은 해당 서비스의 실제 이용권 상태·만료일도 확인한다.
- 통합 계정 운영 권한은 별도로 명시적으로 부여한다. 일반 서비스 관리자는 통합 계정 전체 삭제·다른 서비스 데이터 조회를 할 수 없다.
- 같은 운영자를 두 서비스 관리자로 지정할 수 있지만 각 권한 부여는 별도로 기록한다.

## 5. 가입·로그인·설정 화면

1. 사용자가 어느 사이트에서든 공통 계정을 만들고 이메일을 인증한다.
2. 가입한 서비스의 이용 안내·필요 동의를 완료하면 해당 서비스 회원을 생성한다.
3. 다른 서비스에서는 기존 계정으로 로그인한 뒤 최초 한 번만 서비스 이용 시작을 확인한다. 비밀번호나 공통 닉네임을 다시 만들지 않는다.
4. 서비스 가입 기록과 해당 서비스 프로필은 한 번만 생성되도록 처리한다. 재시도나 동시 접속으로 가입·혜택이 중복 생성되지 않도록 한다.
5. 단순 방문·로그인만으로 탈퇴한 서비스를 자동 재가입시키지 않는다. 재가입 의사를 확인한다.

새로운 통합 포털은 우선 만들지 않는다. 두 사이트 설정에 동일한 내용의 `통합 계정 관리`와 각 사이트의 `서비스 설정`을 제공하고 공통 처리 규칙을 사용한다.

`통합 계정 관리`에는 닉네임·이메일·비밀번호·보안 설정·통합 계정 삭제를 둔다. `서비스 설정`에는 학습 설정·알림·이용권·해당 서비스 탈퇴를 둔다. 다른 서비스 상품이나 가입을 필수 단계로 넣지 않는다.

기본 로그아웃은 현재 사이트의 로그인 세션을 종료한다. 별도로 `모든 기기에서 로그아웃`을 제공할 경우 두 서비스의 세션에 영향을 준다고 안내한다. 전역 잠금·삭제 상태는 이미 발급된 토큰만으로 우회되지 않도록 서버 접근 검사에 반영한다.

두 서비스 모두 이메일 또는 공통 닉네임으로 로그인한다. 닉네임 로그인은 공통 프로필에서 해당 계정을 찾아 Auth의 현재 이메일로 인증한다. 서비스별 프로필의 닉네임·이메일 복사본에 의존하지 않는다. 닉네임에 연결된 이메일은 서버 안에서만 사용하고 조회 API나 오류 메시지로 공개하지 않는다. 닉네임 변경 후에는 새 닉네임 또는 이메일로 로그인하며 이전 닉네임을 로그인 별칭으로 유지하지 않는다.

## 6. 상품·혜택·알림 운영

- 감사 이용권과 세법 이용권은 별개이다. 각각 자동갱신 여부와 종료일을 표시한다.
- 구독 해지는 자동갱신 중단이다. 이미 부여된 정상 이용기간은 만료일까지 유지한다. 서비스 탈퇴·환불과 다른 동작으로 표시한다.
- 추천인 조회는 해당 서비스에 가입한 적격 회원만 대상으로 한다. 공통 닉네임을 검색하더라도 상대가 다른 서비스에만 가입했다면 추천인으로 등록하지 않는다.
- 추천 관계와 지급 이력은 UUID로 연결하여 닉네임 변경에 영향을 받지 않도록 한다.
- 서비스 탈퇴·재가입으로 같은 계정의 추천 보상·무료 체험·현재 한도 창의 사용량을 초기화하지 않는다. 학습 기록과 혜택 지급·사용 제한 기록은 분리한다.
- 서비스별 한도 키에는 서비스 구분을 포함한다. 공통 보안 목적의 요청 제한과 상품의 사용량 한도는 별도로 관리한다.
- 한 서비스에서 알림을 신청해도 다른 서비스의 알림을 활성화하지 않는다. 감사 채용 알림 설정은 감사 서비스에만 적용한다.

## 7. 서비스 탈퇴·재가입·통합 계정 삭제

서비스 탈퇴 시 해당 서비스의 개인 학습 기록·경험치·랭킹 참여·학습 설정·알림 설정을 삭제하고 자동갱신을 중단한다. 해당 서비스의 결제 이용권과 지급받은 잔여 이용기간도 종료한다. 다른 서비스 기록과 이용권, 공통 닉네임·이메일은 유지한다.

탈퇴 처리를 시작하면 해당 서비스의 신규 이용·결제를 차단한다. 진행 중 채점, 늦게 도착한 결제 결과, 예약된 추천 보상이 탈퇴 후 학습 기록·이용권을 다시 만들지 않도록 처리한다. 결제 결과는 정산·환불 확인을 위해 기록하되 종료된 서비스 이용권을 되살리지 않는다. 필수 종료·삭제 처리가 실패하면 탈퇴 완료로 표시하지 않고 재시도한다.

서비스 재가입은 같은 통합 회원 ID를 사용하되 학습 기록과 경험치는 새로 시작하고 기본 이용 상태로 가입한다. 종료된 이용권이나 미사용 기간은 복원하지 않는다. 유효한 제재나 이미 받은 혜택을 재가입으로 우회할 수 없도록 최소 운영 기록은 학습 기록과 분리한다.

탈퇴 전 작업과 재가입 후 작업은 서비스 가입 회차로 구분한다. 같은 회원 UUID로 재가입했더라도 이전 가입 회차의 늦은 작업 결과가 새 학습 기록·이용권에 반영되지 않도록 한다.

서비스 탈퇴 화면에는 삭제 대상, 종료되는 이용권과 원래 만료일, 재가입 시 복원 불가, 다른 서비스에는 영향이 없다는 점을 표시한다. 잔여 이용기간을 유지하려는 사용자는 별도 `자동갱신 해지` 메뉴를 사용할 수 있게 한다. 탈퇴 자체를 자동 환불 완료로 표시하지 않으며, 환불 신청·심사·처리 결과는 별도 환불 정책을 따른다.

개인 학습 기록 삭제가 거래 증빙 삭제·환불·지급 혜택 이력 초기화를 의미하지는 않는다. 결제·환불·정산 및 최소 운영 기록의 보관·삭제 기준은 별도 정책 대상이며, 구체적 법정 보관 기간은 이 문서에서 정하지 않는다.

통합 계정 전체 삭제는 다음 순서로 처리한다.

1. 공통 계정을 삭제 처리 중으로 표시하여 두 서비스의 신규 이용·결제를 차단한다.
2. 두 서비스의 자동갱신 중단과 미처리 결제·환불 상태를 확인한다. 외부 결제 처리가 실패하면 완료로 표시하지 않고 재시도한다.
3. 각 서비스의 삭제 정책을 적용하고 공통 프로필·인증 계정을 삭제한다.
4. 삭제·제재 상태 검사로 기존 세션의 서비스 접근도 차단한다.

문제은행·기준서·세법 자료·수집된 회계법인 데이터 등 서비스 콘텐츠는 회원 개인 학습 기록과 구분한다. 회원 삭제 과정에서 이를 함께 삭제하지 않는다.

## 8. 게스트 운영

게스트 체험은 현재 각 서비스 정책을 유지한다. 익명 세션을 통합 정식 회원이나 서비스 정식 가입자로 집계하지 않고 공통 닉네임을 만들지 않는다. 게스트 기록의 자동 회원 이전은 이번 범위에 추가하지 않는다.

audit_say의 현재 게스트 풀이 결과 보관 기간은 7일이며 영구 프로필·경험치를 만들지 않는다. CTA의 무료 체험·일일 한도는 해당 서비스의 현재 정책을 유지한다. 정식 회원 가입이나 서비스 재가입으로 지급되는 체험 혜택은 별도 서비스 정책을 따른다.

## 9. 구현 시 정리할 기존 구조

- 공통 프로필과 서비스 가입 상태의 정본을 두고, 기존 `cpa_users`·`cta_user`는 서비스 학습·설정 데이터 역할로 정리한다. 역할·유료 상태·공통 닉네임을 여러 위치에서 독립 수정하지 않는다.
- CTA의 모든 비익명 Auth 가입에 CTA 프로필을 만드는 기존 함수를 서비스 첫 이용 절차에 맞춘다. 운영에 연결된 실제 트리거는 구현 전 확인한다.
- audit_say의 프로필 누락 자동 생성과 CTA의 프로필 누락 시 member 처리 때문에 탈퇴·정지 상태가 자동 복구되지 않도록 바꾼다.
- audit_say 풀이 기록은 `auth.users`를 직접 참조하는 반면 오답·경험치 일부는 `cpa_users`를 참조한다. 서비스 프로필 행 하나 삭제로 학습 데이터가 모두 지워진다고 가정하지 않는다.
- CTA 결제·추천 이력의 기존 삭제 연쇄를 점검하여 서비스 탈퇴가 결제 처리 상태를 잃어버리게 만들지 않도록 한다.
- CTA의 닉네임 로그인·추천인 조회를 공통 닉네임에 맞추되, 추천인 자격은 해당 서비스 기준으로 확인한다. 로그아웃은 현재 사이트 세션을 종료하도록 범위를 명시한다.
- 기존 계정 초기화 전에 실제 사용자 참조·결제 상태·관리자 재생성 방식을 확인한다. 계정 UUID에 연결된 결제 식별자도 함께 점검한다.
- 신규 관리자 지정, 두 서비스 최초 가입, 닉네임 변경, 각 서비스 이용권, 서비스 정지·탈퇴·재가입, 전체 계정 삭제의 동작을 확인한 뒤 전환한다.
