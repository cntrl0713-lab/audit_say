## 1. 메모 불일치 시 롤백을 증명하는 회귀 테스트 (우선)

**문제.** `docs/판본-조회-RPC-최적화-2026-09-21.md:128`이 "어긋나면 릴리스까지 되돌린다"의 증명으로 두 테스트 파일을 들지만, 두 파일은 성공 경로(3/3/3, 4/4/4)만 확인한다. `Release source memo incomplete` 경로를 타는 테스트가 없다.

**확인된 사실.** 점검 전에 백필 함수를 0을 돌려주는 스텁으로 바꾸면(점검이 스텁의 정의 해시를 고정하므로 함수 guard는 통과) 적용 SQL이 `Release source memo incomplete`로 실패하고 릴리스·판본·메모·검토 이벤트 행이 하나도 남지 않는다. PGlite 3.5초.

**수정.** `tests/questionReleaseDelta.test.ts`에 helper와 테스트를 추가한다(`memoCoverage` 아래, 'publishes only the corrected set' 테스트 뒤).

```ts
/** 롤백 확인용: 릴리스·판본·메모·검토 이벤트 행 수. 실패한 apply 뒤에 하나도 늘지 않아야 한다. */
async function tableCounts(db: PGlite) {
    return scalar<Record<string, number>>(db,
        "(select jsonb_build_object('releases',(select count(*) from cpa_question_bank_releases),'versions',(select count(*) from cpa_question_set_versions),'memo_items',(select count(*) from cpa_question_bank_release_item_source),'memo_versions',(select count(*) from cpa_question_set_version_source),'events',(select count(*) from cpa_question_review_events)))");
}

test('delta SQL rolls the whole release back when the version source memo is incomplete', async () => {
    const { db, sets, baseline } = await setup();
    try {
        // 점검 전에 백필 함수를 0을 돌려주는 스텁으로 바꾼다. 점검이 스텁의 정의 해시를 고정하므로 함수 guard는 통과하고 메모 대조에서 어긋난다.
        await db.exec(`create or replace function public.cpa_backfill_release_item_source(p_release_id uuid default null) returns int
            language plpgsql volatile security invoker set search_path=pg_catalog,public as $body$ begin return 0; end $body$`);
        const before = { items: await activeItems(db), rows: await tableCounts(db) };
        const next = structuredClone(sets); next[1].subquestions[0].criteria[0].claim += ' 보완';
        const { sql } = await prepared(db, baseline, next);
        await assert.rejects(db.exec(sql), /Release source memo incomplete/);
        await db.exec('rollback');
        assert.deepEqual(await activeItems(db), before.items, 'active release unchanged after the failed apply');
        assert.deepEqual(await tableCounts(db), before.rows, 'no release, version, memo or review-event row survived');
        assert.deepEqual(await memoCoverage(db), { items: 3, memo_items: 0, memo_versions: 0 });
    } finally { await db.close(); }
});
```

## 2. 테스트 fixture의 service_role 쓰기 권한 회수 (우선)

**문제.** `tests/helpers/cpaLearningDatabase.ts:17`의 `alter default privileges in schema public grant all on tables to anon,authenticated,service_role` 때문에 fixture에서 service_role이 메모 표 INSERT 권한을 갖는다. migration은 public·anon·authenticated에서만 회수하므로 그대로 남는다. 따라서 적용 SQL의 `reset role`을 지워도 현재 테스트는 통과한다. 즉 `reset role`이 테스트에서 검증되지 않는다.

**확인된 사실.** 두 메모 표에서 service_role의 insert·update·delete·truncate·references·trigger를 회수하면, 스테이징된 SQL은 그대로 통과(3/3/3)하고 `reset role;` 줄을 뺀 SQL은 `permission denied`로 실패해 되돌아간다.

**수정.**

1. `tests/helpers/cpaLearningUnitsDatabase.ts`에 export를 하나 추가한다.

```ts
/** migration 20260921120000의 의도(메모 표 쓰기는 소유자만)를 fixture에 반영한다. helper의 기본 권한이 service_role에 ALL을 주므로 명시적으로 회수해야 적용 SQL의 역할 복귀가 검증된다. */
export async function revokeMemoWritesFromServiceRole(db: Awaited<ReturnType<typeof createLearningDatabase>>) {
  await db.exec('revoke insert,update,delete,truncate,references,trigger on table public.cpa_question_set_version_source,public.cpa_question_bank_release_item_source from service_role');
}
```

2. `tests/questionReleaseDelta.test.ts` `setup()`의 `await db.exec(memoMigration);` 바로 뒤와 `tests/questionReleaseCli.test.ts:59`(메모 migration 적용) 바로 뒤에 `await revokeMemoWritesFromServiceRole(db);`를 넣고 import를 추가한다.
3. 두 파일의 모든 테스트가 그대로 통과해야 한다. 통과하면 이후로는 `reset role`(§4 뒤에는 `set local role none`)을 빼는 회귀를 테스트가 잡는다.

운영 권한의 실제 값은 §9에서 사용자가 확인한다. `tests/cpaQuestionVersionSourceMemoDatabase.test.ts`는 손대지 않는다(migration의 grant 형상을 그대로 단언하는 테스트이고, 운영 회수 여부는 별도 결정이다. §11).

## 3. 메모 대조 예외에 수치 포함

```ts

    // migration의 의도이므로(테스트 fixture는 그 권한을 명시적으로 회수한다) service_role을 transaction 안에서만 되돌린 뒤 부른다.
    // 채운 행·메모 행·판본 조각이 항목 수와 어긋나면 수치를 담은 예외로 transaction 전체(릴리스 포함)를 되돌린다.
    const memo = `set local role none;\n`
        + `do $delta_memo$ declare new_id uuid; item_count int; written int; memo_rows int; version_rows int; begin\n`

        + `new_id:=current_setting('cpa.delta_new_release_id')::uuid;\n`

        + `written:=public.cpa_backfill_release_item_source(new_id);\n`
        + `select count(*) into memo_rows from public.cpa_question_bank_release_item_source s where s.release_id=new_id;\n`
        + `select count(*) into version_rows from public.cpa_question_bank_release_items i join public.cpa_question_set_version_source v on v.set_version_id=i.set_version_id where i.release_id=new_id;\n`

        + `end $delta_memo$;\n`;
```

## 4. `reset role` 대신 `set local role none`

**문제.** `reset role`은 세션 설정이라 `commit` 뒤에도 남는다. 적용 SQL의 다른 설정은 모두 `set local`이다. 지금은 Management API 세션 사용자가 postgres라 차이가 없지만, 세션에 역할이 걸려 있는 연결이 재사용되면 `reset role`이 그 역할을 지운다.

**확인된 사실.** PGlite에서 `begin; set local role service_role; set local role none; select current_user` → `postgres`, `reset role`과 같다. `reset role`은 advisory lock·`statement_timeout`·`set_config` 값을 지우지 않는다(둘 다 해당).

**수정.** §3의 코드에 포함(첫 줄). 문서 `cpa_uploader/releases/README.md:29`의 "`reset role`로 세션 사용자(표 소유자)로 돌아가"를 "`set local role none`으로 transaction 안에서만 세션 사용자(표 소유자)로 돌아가"로 바꾼다.

## 6. inspect·prepare에서 기준 릴리스의 메모 불완전 경고

**문제.** 증분 적용은 **새 릴리스만** 백필한다. 회차별 퇴역+추가 드라이버로 올린 뒤 수동 백필을 빠뜨리면 inspect가 `memo: {items: N, memo_items: 0, memo_versions: 0}`을 그냥 출력하고 prepare·probe·apply가 진행되며(`pinned()`는 memo를 보지 않음) 그 릴리스에만 묶인 판본은 계속 느린 경로를 탄다.

**수정.** `cpa_uploader/publish_question_release.ts`에 helper를 두고 inspect 분기(397행 뒤)와 `prepareRelease`(171행 `assertReleaseInspection` 뒤)에서 부른다. 막지는 않는다(백필 전에 준비만 해 두는 경우가 있을 수 있다).

```ts
/** active 릴리스의 판본 조회 메모가 불완전하면 알린다. 증분 적용은 새 릴리스만 백필하므로 기준 릴리스의 공백은 이어진다. */
function memoWarning(inspection: ReleaseInspection): string | null {
    const memo = inspection.memo;
    if (memo && memo.memo_items === memo.items && memo.memo_versions === memo.items) return null;
    const id = inspection.active!.release_id;
    return `주의: active 릴리스 ${id}의 판본 조회 메모가 불완전합니다(${JSON.stringify(memo)}). 사용자가 Management API 쓰기 연결(세션 사용자)에서 select public.cpa_backfill_release_item_source('${id}')를 한 번 부른 뒤, 새 --run으로 inspect부터 다시 시작하십시오.`;
}
```

- inspect: `console.log(JSON.stringify({ active..., memo..., ... }))` 다음에 `const warning = memoWarning(inspection); if (warning) console.log(warning);`
- prepare: 같은 호출. 추가로 `preparation.json`에 `baseline_memo: inspection.memo ?? null`을 기록하면 나중에 준비 시점의 상태를 알 수 있다(`Preparation` 인터페이스에 `baseline_memo` 추가).

## 7. migration 전제 조건과 42P01 힌트

**문제.** migration 20260921120000이 없는 DB에서 `releaseInspectionSql()`은 메모 표를 참조하다 `relation ... does not exist`(42P01)로 바로 실패한다. `assertReleaseInspection`의 새 안내("검토 대상 함수가 없습니다")에는 닿지 못하고, 어느 문서에도 전제 조건이 없다.

**수정.** `publish_question_release.ts` `inspect()`(99~102행):

```ts
async function inspect(transport: SqlTransport): Promise<ReleaseInspection> {
    let rows: { inspection: unknown }[];
    try { rows = await transport<{ inspection: unknown }>(releaseInspectionSql(), true); }
    catch (error) {
        if ((error as { sqlstate?: string | null }).sqlstate === '42P01') {
            throw new Error('점검 SQL이 참조하는 표가 없습니다. migration 20260921120000_cpa_question_version_source_memo.sql이 적용된 프로젝트에서만 inspect·probe·apply·verify를 실행할 수 있습니다.', { cause: error });
        }
        throw error;
    }
    return assertReleaseInspection(rows[0]?.inspection);
}
```

## 8. 테스트 보강 두 가지

**8-1. 백필 함수 재정의가 probe·apply를 멈추는지.** README와 RPC 문서가 약속하지만 테스트는 `cpa_normalize_fact`만 바꿔 본다. `tests/questionReleaseDelta.test.ts`에 추가:

```ts
test('delta SQL stops when the memo back-fill function changes after the inspection', async () => {
    const { db, sets, baseline } = await setup();
    try {
        const before = await activeItems(db);
        const next = structuredClone(sets); next[1].subquestions[0].criteria[0].claim += ' 보완';
        const { sql, probe } = await prepared(db, baseline, next);
        await db.exec(`create or replace function public.cpa_backfill_release_item_source(p_release_id uuid default null) returns int
            language plpgsql volatile security invoker set search_path=pg_catalog,public as $body$ begin return 0; end $body$`);
        for (const text of [probe, sql]) {
            await assert.rejects(db.exec(text), /Reviewed function changed: cpa_backfill_release_item_source\(uuid\)/);
            await db.exec('rollback');
        }
        assert.deepEqual(await activeItems(db), before);
        assert.deepEqual(await memoCoverage(db), { items: 3, memo_items: 0, memo_versions: 0 });
    } finally { await db.close(); }
});
```

## 10. 검토에서 확인된 것 (다시 조사하지 않는다)

- 두 릴리스 테스트 파일 7건, `tsc --noEmit`, 대상 파일 eslint 모두 통과(2026-09-22).
- `reset role`은 advisory xact lock·`statement_timeout`·`cpa.delta_prior_*` 값을 지우지 않는다. 세션 사용자=표 소유자(postgres) 표현은 정확하다.
- probe SQL에도 `functionGuards`가 들어가므로 백필 함수 정의가 바뀌면 probe·apply 모두 멈춘다.
- 옛 실행 폴더(`cpa_uploader/releases/20260919-*`)는 memo 키가 없지만 이전 guard("이미 준비한 실행", `pinned()` 불일치, "이미 검증을 마친 실행")에서 멈추므로 호환 문제가 없다.
- importer가 기존 릴리스를 재사용(`reused=true`)하는 경우는 `$delta_after$`의 `into strict`가 먼저 실패해 memo 블록에 닿지 않는다.
- 방안 4 마무리(import RPC가 메모 행을 직접 씀) 뒤에도 `rows_written`은 `on conflict do nothing`과 무관하게 항목마다 증가하므로 `written == item_count`는 유지된다.
- 압축 전송 경로도 같은 memo 블록을 타며 3/3/3이 확인되었다.
- `apply-response.json`에는 importer 영수증 행만 남는다(memo 블록은 행을 돌려주지 않음). 메모 증거는 `verification.json`의 `memo`다.
- 런타임 모듈(`questionReleaseDelta.ts`, `publish_question_release.ts`)의 해시를 고정한 receipt는 없다. 수정해도 과거 기록이 깨지지 않는다.

## 11. 사용자 실행 항목과 범위 밖 결정

**사용자 실행(읽기 전용).** 운영에서 service_role이 메모 표에 쓰기 권한을 갖는지 확인한다. 결과를 이 문서 아래에 기록한다.

```sql
select has_table_privilege('service_role','public.cpa_question_bank_release_item_source','insert') as item_insert,
       has_table_privilege('service_role','public.cpa_question_set_version_source','insert') as version_insert;
```

- 둘 다 `false`면 §3 주석의 전제가 운영에서도 성립한다. 끝.
- 하나라도 `true`면 migration이 기본 권한을 회수하지 않은 것이다. 적용 경로는 `set local role none`을 쓰므로 동작에는 영향이 없다. 최소 권한을 맞추려면 `revoke insert,update,delete,truncate,references,trigger on table ... from service_role`을 담은 **새 migration**을 만들고 사용자가 적용한다. 이는 이 계획의 범위 밖이며 별도로 결정한다. 기존 migration 파일은 고정되어 있어 고치지 않는다.

**범위 밖.** 회차별 드라이버에 백필 단계를 넣는 일(사본은 고정, 공용 도구로 옮길 때 같은 transaction 백필을 넣는다), 방안 4 마무리 migration.
