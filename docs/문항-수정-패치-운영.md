# 문항 수정 패치 운영

게시된 문항 하나를 고칠 때 정본 전체를 다시 쓰거나 복사하지 않도록 수정 경로를 바꾼다. 사용자가 2026-09-19에 제공한 「GitHub·Supabase 해결책 발전 과정과 최종 개선안」(저장소 밖 문서)의 제안을 이 저장소의 실제 구조에 맞게 비판적으로 받아들였다. 사용법은 [correction 안내](../cpa_uploader/corrections/README.md)와 [운영 반영 기록 안내](../cpa_uploader/releases/README.md)에 있다.

## 바꾸기 전: 한 번의 수정이 전체 사본을 만든 경로

기존 문항 수정(예: 2026-09-14 관찰 O1–O3, 10세트)은 다음을 거쳤다.

1. 편집 정본 전체를 복사한 수정본(`evidence-bank.json`, 약 6MB)과 기준 사본(`baseline/authoring.json`, `baseline/ledger.json`)을 검토 폴더에 만들었다.
2. 대표 채점 manifest가 그 전체 은행 사본과 전체 분류 카탈로그를 바이트로 고정했다. 과거 receipt를 다시 검증하려면 사본이 계속 저장소에 있어야 했다.
3. 회차마다 게시 스크립트(`publish.mjs`)와 운영 DB 드라이버(`db-incremental-v1/driver.mjs`, `replace-contract.mjs`)를 복사해 고쳤다.
4. 게시 때마다 분류 입력 전체(551항목)를 새 파일로 만들었다. 카탈로그 검사가 입력 파일에 정본 해시를 고정하기 때문이다.

2026-09-19 HEAD 기준으로 `cpa_uploader/data/` 밖에 커밋된 4MB 초과 JSON이 60개(560MB)다(생성물 `question-elements.json`·`registry.json` 제외). 그중 은행·후보·기준 사본이 39개(202MB), 원자료 카탈로그 사본이 13개, 승급 장부 사본이 5개다. 2026-09-15 r01–r04 게시 커밋은 1,003개 파일을 바꿨다.

## 바꾼 뒤: 수정 한 건이 남기는 것

| 산출물 | 크기 | 저장소 |
| --- | --- | --- |
| `cpa_uploader/corrections/<id>.json` — 바꿀 필드, 수정 전 값, 이유 | 수 KB | 커밋 |
| 검수용 부분 은행·카탈로그·검사 기록(수정 세트만) | 세트당 약 17KB | 검토 배치에 커밋 |
| 정본 변화 — 대상 세트의 줄, 공개본의 해당 세트, 승급 장부 두 항목, 분류 입력·카탈로그의 머리글 해시와 해당 항목. 암호화본은 전체가 다시 암호화된다(아래 남은 일 1) | 필드 하나 수정이면 정본 1줄 | 커밋 |
| `cpa_uploader/corrections/applied/<id>.json` — 적용 기록 | 수 KB | 커밋 |
| `cpa_uploader/releases/<run>/*.json` — 운영 반영 기록 | 수십 KB | 커밋 |
| 스테이지 사본, 비교용 전체 은행, 적용 SQL, 준비 검사 보고서 | MB 단위 | `tmp/`(커밋 안 함), 기록에는 해시만 |

회차별 스크립트를 복사하지 않는다. 게시는 `cpa_uploader/correct_cpa_v3.ts publish`, 운영 반영은 `cpa_uploader/publish_question_release.ts`가 맡는다. 두 도구는 기존 승급·컴파일·검증·카탈로그 도구와 importer를 그대로 호출한다. 검수 receipt가 고정한 런타임 파일(`EFFICIENT_RUNTIME_FILES`)은 바꾸지 않았다.

## 제안을 받아들인 방식

| 제안 | audit_say의 판단 | 이유 |
| --- | --- | --- |
| 스키마와 콘텐츠 분리 | 유지 | 콘텐츠는 이미 importer RPC로만 들어가고 마이그레이션에 문항 DML이 없다 |
| 문제 단위 artifact 파일 | 수정 명세만 세트 단위 파일로 둠. 정본 분할은 보류 | 정본 직렬화가 결정적이라 세트 줄만 바뀐다. 검증기·receipt·wiki·분석이 정본 한 파일을 가리키므로 분할의 이득보다 이관 위험이 크다 |
| correction 최소 계약(target, reason, expected_before, set) | 채택 | 대상은 DB 키가 아니라 안정 ID(세트·물음·criterion·requirement·출처·사실)로 지정한다. 세트 전체의 `base_content_hash`를 더해 다른 필드의 동시 수정도 막는다 |
| review 불리언 플래그 | 거절 | 스스로 적는 체크는 검수 증거가 아니다. `publish`는 실제 검수 receipt(`--efficient-review` 또는 `--review`)를 필수로 받고 승급 도구가 검증한다 |
| 멱등성 | 채택 | 적용 기록이 있는 correction은 다시 설치하지 않는다. 운영에서는 active 릴리스 ID·원문 해시로 비교 후 교체(CAS)하고, 같은 SQL을 다시 보내면 거절한다 |
| allowlist | 채택 | ID·수명주기 라벨·주제 구조·물음 구성·답안 정책은 대상이 아니다. 세트 추가·삭제·재정렬도 이 경로가 받지 않는다 |
| transaction | 채택 | 파일: 스테이지 검증 후 입력 해시 가드로 원자 교체하고, 설치 후 검사가 실패하면 되돌린다. DB: 역할·잠금·함수 정의·기준 원문 확인, importer 호출, 사후 검증을 한 transaction으로 묶는다 |
| 수정 전후 스냅샷 | 채택 | 명세의 `expected_before`/`set`, 적용 기록의 내용 해시 전후, 운영 `before.json`/`verification.json` |
| manifest hash | 채택 | 명세 SHA-256·git blob을 적용 기록과 승급 근거에 남긴다. 운영 적용은 검토한 `preparation.json`의 SHA-256을 인자로 요구한다 |
| staging 검증 | 로컬 PostgreSQL로 대체 | 공유 프로젝트에 Supabase Branch를 쓰는 비용과 위험 대신 PGlite에서 실제 마이그레이션·importer로 복원을 증명하고, 운영에서는 읽기 전용 probe로 같은 해시를 확인한다 |
| `cta_content_corrections` 같은 원장 테이블 | 만들지 않음 | audit_say DB는 이미 봉인 버전·릴리스·append-only 검수 이벤트를 갖는다. correction ID와 명세 해시를 검수 이벤트의 evidence에 남기고, 파일 쪽 `applied/` 기록이 correction 단위 원장이다. 운영 공유 DB에 스키마를 늘리지 않는다 |
| draft/approved/conflict/rejected 상태 저장 | 저장하지 않음 | 충돌·거절은 쓰기 전에 실패하며 흔적을 남기지 않는 편이 정확하다(CTA와 같은 판단) |
| DB 반영과 공개 분리(release) | 기존 모델 유지 | active 릴리스 포인터가 이미 공개 상태다 |
| audit-say 마이그레이션 도메인 검사 | 이번 범위 밖 | 수정 경로와 별개다. `common_accounts` 마이그레이션이 의도적으로 `cta_user`를 바꾸므로 허용 목록과 함께 설계해야 한다 |

## 계층별 역할

| 계층 | 역할 | 바꾸는 주체 |
| --- | --- | --- |
| `cpa_uploader/data/cpa_question_sets_v3.authoring.json` | 편집 정본 | 제작 경로의 편입 도구, 수정 경로의 `publish` |
| `cpa_uploader/corrections/*.json` | 게시 문항의 변경 요청 | 사람·에이전트가 작성, 게시 후 불변 |
| `cpa_uploader/corrections/applied/` | 정본 설치 원장 | `publish`만 |
| `cpa_question_sets_v3.promotions.json` | 검수·게시 근거 | 승급 도구 |
| 공개본·암호화본·분류 카탈로그·분류 입력 | 생성물 | 컴파일·카탈로그 도구(`publish`가 호출) |
| 운영 `cpa_question_set_versions`·`cpa_question_bank_releases` | 운영 상태(봉인 버전, active 릴리스) | importer RPC |
| 운영 `cpa_question_review_events` | 운영 원장(append-only) | importer RPC |
| `cpa_uploader/releases/<run>/` | 운영 반영 증거 | `publish_question_release.ts` |

## 검증

- `tests/questionCorrection.test.ts`: 계약 파서(키·ID·이유·효과 없는 패치·겹침·값 형상), 대상 표기 왕복, 동시 수정·재적용 거절, 없음과 null 구분, 65세트 격리 은행의 전체 검증, 필드 하나 수정이 정본 1줄 변화인지, 분류 이어받기 규칙, 부분 은행 카탈로그가 대표 채점 검증기 규칙을 만족하는지.
- `tests/questionCorrectionCli.test.ts`: 격리 은행에서 비계 → 검사 → 부분 증거 → 스테이지만 → 설치 → 재설치 거절. 설치 후 승급 장부는 두 항목만 늘고, 공개본은 그대로이고, 암호화본은 새 정본으로 복호화되며, 카탈로그 검사와 전체 은행 검증을 통과한다. 오래된 명세는 스테이지 전에 거절한다.
- `tests/questionReleaseDelta.test.ts`: 실제 마이그레이션·importer를 올린 PGlite에서 교체 세트만 새 버전이 되고 나머지 버전은 재사용된다. 끝에 추가도 된다. 재전송·변조 패치·검토 후 바뀐 함수 정의는 쓰기 없이 거절한다.
- `tests/questionReleaseCli.test.ts`: 운영 전송을 PGlite로 바꿔 inspect → prepare → probe → apply(1회) → verify 전 과정을 실행한다.
- `tests/questionCorrectionArtifacts.test.ts`: correction 이름·형식·크기, 게시 후 명세 불변, 릴리스 폴더에 SQL·사본이 없는지.
- `tests/questionReleaseDelta.test.ts`·`tests/questionReleaseCli.test.ts`의 압축 전송 검사: pgcrypto를 `extensions` 스키마에 둔 PGlite에서 압축 pack이 평문과 같은 payload로 복원되고, 틀린 암호와 공개 암호로 다시 만든 변조 pack은 쓰기 없이 거절되며, inspect → prepare(`--transport compressed`) → probe → apply → verify가 통과한다.
- 2026-09-19 기준서형 검토 반영(181세트 교체)에서 평문 전송 probe가 Management API의 요청 크기 제한(HTTP 413, 본문 3.35MB)에 걸렸다. 읽기 전용 단계라 쓰기는 없었다. 2026-09-14 전례(압축 전송, 1.82MB 통과)를 이 도구의 `--transport compressed`로 옮겨 요청을 0.49MB로 줄였고, probe·apply가 통과했다(릴리스 `c43c59e4`).
- 같은 반영의 첫 verify는 service_role 전용 조회 함수를 읽기 전용 API 계정(`supabase_read_only_user`)으로 불러 권한 오류로 멈췄다. read only transaction 안에서 service_role로 부르게 고쳐 통과했다. `tests/questionReleaseCli.test.ts`의 로컬 전송은 이제 읽기 전용 요청을 표만 읽을 수 있는(RLS 우회, 함수 권한 없음) 역할로 실행하며, 고치기 전 코드로는 운영과 같은 오류로 실패한다.
- 2026-09-19 로컬 리허설(운영 접속 없음): 현재 정본 369세트(6.2MB)를 PGlite에 올리고 세트 하나를 고쳐 증분 게시했다. 전송 SQL은 215KB(바뀐 세트 7.7KB + importer가 요구하는 전체 물음 분류 197KB), 적용 약 2초, 새 버전은 그 세트 하나였다. 이 리허설에서 첫 세트를 고치면 로컬 변조 검사가 무력해지는 결함을 찾아 고쳤다.

## 남은 전체 사본과 결정할 일

1. 암호화본(`data/cpa_question_sets_v3.authoring.enc.json`, 약 8MB)은 한 덩어리 암호문이라 설치 때마다 전체가 바뀐다. 세트별 암호화는 파일 모드 런타임을 바꿔야 한다.
2. 운영 릴리스마다 importer가 정본 원문 전체(약 6MB)를 `source_document`에 저장한다. 전송은 증분이지만 저장은 누적된다. `inspect`가 누적 크기를 보여 준다. 줄이려면 importer 마이그레이션이 필요하다.
3. 기존 검토 폴더의 전체 은행 사본은 과거 receipt가 바이트로 참조하므로 그대로 둔다. 옮기려면 해당 receipt의 재검증 경로가 필요하다.
4. 새 작업이 전체 은행 사본을 커밋하지 못하게 막는 저장소 전체 게이트는 진행 중인 사례형 검토 회차(r05~r07)가 커밋된 뒤 도입을 검토한다. 지금 넣으면 그 회차의 커밋이 막힌다.
5. `wiki:build`는 여전히 모든 생성 페이지의 날짜를 바꾼다. [wiki SCHEMA](../cpa_uploader/wiki/SCHEMA.md)의 되돌리기 규칙을 따른다.
