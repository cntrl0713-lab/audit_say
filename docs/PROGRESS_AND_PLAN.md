**PRD보다 더 한 것** — 부문별 **인원**은 PRD가 "1차 선택 수집"으로 뒀지만, 직원 현황

없어 P2 원문 파싱으로 넘긴다.

> **⚠ 검증하지 못한 것 — 이 문서에서 가장 중요한 한 줄**
>
> **엔드포인트 경로와 응답 필드명을 실호출로 확인하지 못했다.** OpenDART 개발가이드

### 2-3. M2 — 분석 레이어 검증 (커밋 `d2426b7`)

뷰 5개는 M0에서 만들었으므로 M2에 남은 것은 "파생 지표 계산 검증"이었다.
일회성 확인 대신 **반복 실행 가능한 스크립트**로 만들었다.

**산출물** — `supabase/verification/verify_firm_views.sql`

전체가 한 트랜잭션이고 마지막이 `ROLLBACK` 이라 몇 번을 돌려도 데이터가 남지 않는다.
어긋난 값이 하나라도 있으면 그 자리에서 예외를 던진다.

**왜 필요한가** — 뷰의 집계는 데이터가 없으면 0행이다. "쿼리가 돈다"는 것으로는
아무것도 증명하지 못한다. 다음은 값을 넣어야만 알 수 있다.

| 확인 | 왜 |
|---|---|
| `data_status <> 'ok'` 행이 평균에서 빠지는가 | 금융사 결측이 섞이면 평균이 통째로 왜곡된다 |
| 1인당 매출·급여, 이사 대비 직원, 감사부문 비중 | PRD §4.2-C 파생 지표의 분자·분모 |
| 분모가 없을 때 0 이 아니라 NULL 인가 | 0 을 주면 "1인당 매출 0원"이라는 거짓말이 된다 |
| 고객사 없는 법인이 연도 축에 남는가 | 자체 지표만 있는 법인이 사라지면 안 된다 |
| 용역 없는 engagement 행이 사라지지 않는가 | LEFT JOIN 이 INNER 로 바뀌는 회귀를 잡는다 |
| 감사 이력 첫 연도가 `false` 가 아니라 `NULL` 인가 | 첫 기록은 "변동 없음"이 아니라 "비교 대상 없음"이다 |
| 숨김 리뷰가 집계와 `recent_reviews` 에서 빠지는가 | 관리자 숨김이 뚫리면 안 된다 |
| `recent_reviews` 에 `user_id` 가 없는가 | 익명성 |

**역대조** — 어서션에 이빨이 있는지도 확인했다. 결측 행의 `data_status` 를 `ok` 로
바꿔 넣으면 평균이 1000 → 5499.5 로 바뀌어 검증이 실패한다. 통과가 우연이 아니다.

- `app/(firm)/companies/page.tsx` — 검색·시장 필터·페이지네이션
- `app/(firm)/companies/[corp_code]/page.tsx` — 재무 3지표·감사 이력·KAM
- `app/(firm)/_components/ui.tsx` — 공용 UI
- `lib/firm/format.ts` — 표시용 포매터
- `lib/firm/params.ts` — searchParams 읽기·쓰기

**설계 방침**

- 상태(검색·필터·정렬·페이지·탭·연도)는 **전부 URL** 에 둔다. 서버에서 렌더하고 그대로
  공유·북마크할 수 있다. 필터마다 클라이언트 상태를 들 이유가 없다.
- 검색은 평범한 GET 폼이라 **자바스크립트 없이도 동작**한다.
- **결측은 0 이 아니라 `-`**, **음수는 하이픈이 아니라 마이너스 기호(−)**.
  표에서 손실을 결측으로 읽으면 안 된다.
- **"수집 전"과 "필터 결과 없음"을 다른 화면으로 구분**한다. 사용자가 필터를 잘못
  걸었다고 오해하면 안 된다.

**검증** — 빌드 통과로는 화면이 맞는지 알 수 없어서, 임시 데이터를 넣고 앱을 실제로
띄워 대조한 뒤 되돌렸다.

| 항목 | 화면 | 손계산 |
|---|---|---|
| 1인당 매출 | 2.6억원 | 1.08조 ÷ 4,100명 |
| 평균 KAM | 1.3 | (2+1+1) ÷ 3 |
| 이사 대비 직원 | 12.8배 | 4,100 ÷ 320 |
| 감사부문 비중 | 60.0% | 648 ÷ 1,080 |
| 감사보수 합계 | 23.6억원 | 18.5 + 4.1 + 0.95 |
| 비감사 비중 | 17.5% | 5 ÷ 28.55억 |

필터(상장·시장·의견)·이름 검색·감사인 교체 감지·잘못된 id 의 404 도 확인했다.

**띄워보지 않았으면 놓쳤을 두 가지를 이 과정에서 고쳤다.**

1. `/firms` 에 연도 선택이 없어 데이터가 적은 최신 연도에 착지했다.
2. 감사 이력의 "의견 변경 (적정 →)" 표기가 화살표 방향을 알 수 없었다.

### 2-5. 부수 작업 — 기준서 검색 계층 정리 (이전 기록)

기준서 원문을 원격 검색 계층에 색인하던 실험 코드는 사용처가 없어 제거 대상으로
확정했다. 현재 출제·채점은 로컬 원문과 v3 `source_quote` 검증을 사용하며, 원문 근거
자료는 문제은행 검증에 필요하므로 보존한다.

이 기록은 당시 조사 결과를 보존하는 역사 문서다. 현재 구현 상태와 삭제 목록은
[`docs/plans/openai-migration-and-gemini-cleanup-plan.md`](plans/openai-migration-and-gemini-cleanup-plan.md)의
Slice 4를 기준으로 한다. 원격 계정의 공유 검색 자산은 식별 전까지 삭제하지 않는다.

## 3. PRD와 달라진 점

전부 `docs/firm-platform-schema.md` 에 근거와 함께 적혀 있다. 요지만 옮긴다.

| PRD | 실제 | 이유 |
|---|---|---|
| `company` · `users` · `subscriptions` · `chat_messages` | `firm_company` · `firm_subscription` · `firm_chat_message` | `cta_*` / `cpa_*` 가 공유하는 스키마라 무접두어 이름은 충돌한다 |
| `users` 테이블 신설 | **만들지 않음.** `user_cpa` 재사용 | 같은 사이트의 같은 계정이다 |
| `engagement.rcept_no` UNIQUE | UNIQUE 아님. `(firm_id, corp_code, bsns_year)` 가 중복 방지 키 | 공동감사면 한 접수번호에 감사인이 둘이라 두 번째 적재가 조용히 실패한다 |
| `v_company_audit_history` | `v_firm_company_audit_history` | 뷰 이름을 `v_firm_` 으로 통일 |
| `audit_opinion.adt_opinion` | 정규화값 + `adt_opinion_raw` 원문 | 정규화 규칙이 바뀌어도 재수집 없이 다시 파싱할 수 있어야 한다 |
| `firm_reviews` | `is_hidden`, `report_count` 추가 | PRD §8 의 신고·숨김 정책을 담을 필드가 없었다 |

## 4. 확정되지 않은 것

**이 절이 다음 작업의 병목이다.** PRD에 문장이 있다고 결정된 것은 아니라서,
"PRD에 적힌 것"과 "결정된 것"을 나눠 적는다.

### 4-1. 챗봇 LLM — **미정**

PRD §1.3·§5.3 에 단일 AI 엔진이라고 적혀 있으나 **챗봇 공급자는 결정되지 않았다.**
이번 OpenAI 전환은 회계감사 문제 출제·채점에만 적용하며, `app/(firm)/chat/page.tsx`의
미정 상태는 유지한다.

정하려면 아래에 답이 있어야 한다. 모델 비교는 이 답이 나온 뒤에 하는 것이 순서다.

| 질문 | 왜 필요한가 |
|---|---|
| 월 예상 질문 수와 1회 질문당 허용 비용은? | 모델 단가 차이가 여기서 갈린다 |
| 첫 응답 목표 10초(PRD §11)를 지킬 것인가? | 스트리밍 필요 여부와 모델 급이 정해진다 |
| 답변을 자유 서술로 낼 것인가, 정해진 틀로 낼 것인가? | 구조화 출력 신뢰도가 모델 선택 기준이 된다 |
| 기존 채점 시스템과 같은 공급자로 묶을 것인가? | 키·요금·장애 영향 범위가 한 곳으로 묶인다 |
| 데이터가 플랫폼 밖으로 나가는 것에 제약이 있는가? | 공개 공시 데이터라 제약이 약하지만, 리뷰 텍스트는 다르다 |

**설계상 더 중요한 논점** (모델 선택과 별개, PRD §13-3):

> 환각을 **프롬프트로 막을 것인가, 구조로 막을 것인가.**

PRD의 "답변에 근거 데이터 출처 표시" 요구를 지키려면, 자유 생성보다
**질문 → 정해진 쿼리 → 결과를 문장으로** 가 유리하다. 어느 행에서 나온 숫자인지
추적할 수 있기 때문이다. 이 결정은 모델을 바꿔도 남으므로 먼저 정하는 편이 낫다.

### 4-2. 그 밖에 미정인 것

| 항목 | 현재 | 정해야 할 것 |
|---|---|---|
| 재직 인증 방식 (PRD §13-1) | 이메일 도메인 인증 "우선 고려"까지만 | 회계법인 메일 도메인 목록 확보 방법, 대체 수단 |
| 평점 항목 (PRD §13-4) | 6항목·1-5척도·5직급을 CHECK 로 박아 둠 | M6 착수 전 최종 확정. 바꾸려면 마이그레이션 필요 |
| 리포트 다운로드 형식 | PRD는 "웹 뷰 + 다운로드"까지만 | PDF / XLSX / 브라우저 인쇄 중 무엇 |
| 무료 공개 범위 (PRD §13-5) | 미정 | 리포트·챗봇을 어느 수준까지 미리보기 허용 |
| 결제 | **나중으로 결정됨** | 당분간 무료 또는 관리자 수동 권한 부여 |
| 등록회계법인 마스터 | 법인명 14곳, 등록번호·군 전부 NULL | 금감원 등록회계법인 목록 출처 |
| `cpa_uploader/references/` | 남겨 둠 (1.4M) | 삭제 여부 |

## 5. 실행 계획

### P0. 실데이터 수집 — **다른 모든 것의 선행 조건**

M4·M5는 데이터가 없으면 착수해도 검증할 대상이 없다. M3 화면도 지금은 빈 껍데기다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| P0-1 | OpenDART 인증키 | 완료: 환경변수 설정 및 실호출 확인 |
| P0-2 | 회사 1곳 프로브 → **필드명 대조** | 완료: 삼성전자 두 연도 의견·KAM·재무 대조. 보수는 사용자 결정으로 제외 |
| P0-3 | 응답 매핑 수정 | 완료: 당기·중복·선택 필드·외화·법인 식별 교정 및 테스트 |
| P0-4 | 종목코드 보유 회사 전량 조회 (2024·2025) | 완료: 각 3,989곳, 식별 가능한 데이터 적재 및 누적 보고서 저장 |
| P0-5 | 미매칭 감사인 재처리 | 완료: 유일 고유번호 신규 35곳·확인된 alias 반영. 동명·오타 등 불확실 건은 사용자 승인에 따라 보류 |
| P0-6 | 회계법인 인력·재무 API 조회 | 조회 완료, 데이터 확보 보류: 59곳 빈 응답·4곳 고유번호 미확정. 원문 파싱 제외 |
| P0-7 | 등록회계법인 마스터 백필 (등록번호·군) | 보류: 출처 미확보. 일반 DART 법인 코드로 등록 여부를 추정하지 않음 |

**리스크** — P0-2 에서 필드명이 크게 어긋나면 P0-3 이 커진다. 다만 파싱·정규화 로직은
이미 테스트로 고정돼 있어, 고칠 곳은 **필드 접근 지점 한 겹**이다.

**예상** — P0-1~P0-3 은 반나절. P0-4 는 상장사 약 2,500곳 × 4회 호출 = 1만 회로
일일 한도 안에서 한 번에 돈다.

### M4. 자동 보고서 (선행: P0)

PRD §5.2 의 8개 절. 데이터는 이미 뷰에 다 있다.

| 절 | 원천 |
|---|---|
| 1 개요 · 2 포트폴리오 요약 · 3 재무 규모 분포 | `v_firm_summary`, `v_firm_clients` |
| 4 의견·KAM 특징 · 5 의견변형 회사 목록 | `v_firm_kam`, `v_firm_clients` |
| 6 용역 요약 · 7 인력·운영지표 | `getFirmContractSummary`, `v_firm_summary` |
| 8 연도별 변화 | `v_firm_summary` 다년 |

**착수 전 정할 것** — 다운로드 형식(4-2 참조), 회원 판별 기준(`user_cpa.role`).

**완료 기준** — 법인 하나를 골라 8개 절이 모두 값으로 차고, 웹 뷰와 다운로드본의
숫자가 일치한다.

### M5. 챗봇 (선행: P0 + 4-1 결정)

**착수 전 정할 것** — 4-1 의 질문들. 특히 "프롬프트로 막을 것인가 구조로 막을 것인가".

**뼈대는 LLM 비종속으로 짤 수 있다.** 아래는 모델과 무관하게 먼저 만들 수 있다.

1. 법인 컨텍스트 고정 (`firm_id` 를 세션에 묶고 질의를 그 범위로 제한)
2. 질의 유형 분류와 대응 쿼리 목록 (PRD §5.3 예시 질문 4종이 출발점)
3. 근거 표시 규격 — 어떤 뷰의 어떤 행에서 나온 숫자인지
4. `firm_chat_message` 이력 저장 (테이블은 이미 있음)
5. 접근 제어 — 결제가 나중이므로 당분간 `user_cpa.role` 기반

모델 호출은 위 뼈대의 마지막 한 겹이다. **어댑터 경계를 두면 모델 결정을 미룰 수 있다.**

**완료 기준** — PRD §5.3 예시 질문 4개에 대해 플랫폼 데이터 범위 안에서 답하고,
답변마다 근거 행을 제시한다.

### M6. 평점 (선행: 4-2 의 재직 인증 정책)

**DART 데이터와 무관하게 완결된다.** P0 가 막혀도 진행할 수 있는 유일한 기능이다.

이미 있는 것: `firm_review` 테이블, `v_firm_reviews_summary` 뷰, RLS 정책,
숨김·익명성 검증(`verify_firm_views.sql`).

남은 것: 인증 정책 확정 → 작성 폼 → 열람 화면 → 신고·숨김 운영 도구.

**착수 전 정할 것** — 재직 인증 방식, 평점 항목 최종 확정(바꾸려면 CHECK 마이그레이션).

**주의** — `firm_review.user_id` 가 공개 조회에 노출된다. 실명·이메일은 없지만 같은
작성자의 리뷰끼리 묶이는 것은 드러난다. 익명성을 더 조이려면 공개 읽기를 `user_id` 없는
뷰로 옮기고 테이블 정책을 본인 행으로 좁힌다 (`docs/firm-platform-schema.md` §4-2).

### P2. 2차 확장 (PRD §4.3)

비상장회사 감사보고서 원문 파싱 / 금융회사 재무 보완 / KAM 주제 분류 /
사업부문별 **매출** 정밀 파싱 (인원은 M1에서 이미 처리).

### 순서에 대한 권고

```
P0 (데이터 수집)  ─┬─→ M4 리포트 ─→ M5 챗봇
                   └─→ M3 화면이 실제로 쓸모 있어짐
M6 평점  ── P0 와 무관하게 병행 가능 (인증 정책만 정하면)
```

DART 키를 기다리는 동안 할 수 있는 일은 **M6 인증 정책 수립**과 **M5 뼈대 설계**다.
