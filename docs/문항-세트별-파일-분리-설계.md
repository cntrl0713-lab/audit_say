# 문항을 세트별 개별 파일로 관리하는 설계

현재 편집 정본은 `cpa_uploader/data/cpa_question_sets_v3.authoring.json` **한 파일에 343세트 6.2 MB**다. 이를 세트마다 파일 하나로 나누고, 지금의 정본 파일은 **생성물로 같은 경로에 같은 바이트로** 유지한다.

## 1. 이 설계가 푸는 것과 풀지 않는 것

먼저 분명히 해 둔다. **대부분의 문제가 풀리지는 않는다.** 푸는 것은 "작업 편의" 계열이고, 오늘 겪은 차단 계열은 대부분 그대로다.

| 문제 | 해결 | 설명 |
| --- | --- | --- |
| 세션 간 정본 충돌 | **예** | 서로 다른 세트를 고치면 파일이 겹치지 않는다. 생성물 충돌은 재생성으로 기계적으로 푼다 |
| diff·리뷰 가독성 | **예** | 2026-09-21 커밋에서 정본 한 파일이 53,630줄 변경으로 잡혔다. 실제로 바뀐 것은 세트 수십 개다 |
| 도구의 전체 파싱 | **예** | 세트 하나가 필요한 도구가 6.2 MB를 읽지 않아도 된다 |
| 판본 조회 RPC timeout | **아니오** | DB가 저장하는 것은 릴리스당 문서 하나다. 저장소 파일 배치와 무관하다. [RPC 최적화](판본-조회-RPC-최적화-2026-09-21.md)로 따로 푼다 |
| 승급 장부 12 MB | **아니오** | 정본보다 크다. 별도 설계가 필요하다 |
| pre-commit 게이트 17~20분 | **아니오** | 전체 테스트 시간이 지배한다 |
| 독립 검증 ~300초 | **아니오** | 판본 343개 순차 조회가 지배한다. 2026-09-22 메모 migration([RPC 최적화](판본-조회-RPC-최적화-2026-09-21.md)) 적용 뒤 86초 |
| receipt의 바이트 고정·CRLF | **아니오** | 오히려 이 설계가 **깨뜨리지 않도록** 지켜야 할 제약이다 |
| 정본 설치의 직렬화 | 부분 | 생성물과 장부는 여전히 한 번에 하나씩 써야 한다 |

즉 **읽고 고치고 리뷰하는 일이 편해지는 변경**이지, 성능이나 검증 시간을 고치는 변경이 아니다.

## 2. 현재 구성 (2026-09-21 실측)

| 항목 | 값 |
| --- | --- |
| 세트 | 343 (사례형 36 · 기준서형 307 · 혼합 0) |
| 기준서형 세트의 물음 수 | 1물음 **248** · 2물음 56 · 3물음 1 · 4물음 2 |
| 세트 크기 | 중앙값 11.5 KB · 최대 177 KB · 최소 4.5 KB |
| 정본 파일 | 6.2 MB |
| 배열 순서 | **id 정렬이 아니라 삽입 순서** |
| 직렬화 | `JSON.stringify(bank, null, 2) + "\n"`로 **바이트 재현 가능**(확인함) |

## 3. 왜 세트 단위인가 — 기준서형도 물음 단위로 쪼개지 않는다

"이론형은 물음 단위, 사례형은 문제 단위"라는 착상은 학습 단위 계약(`<세트>--<물음>--standard` / `<세트>--case`)과 정확히 맞물린다. 그러나 두 가지 때문에 **세트 단위로 통일**한다.

1. **이득이 작다.** 기준서형 세트의 **81%(248/307)가 이미 1물음**이다. 물음 단위로 쪼개도 파일이 343개에서 407개로 **64개 느는 데 그친다.**
2. **대가가 크다.** 세트는 게시·퇴역·판본·릴리스 항목의 단위다. `cpa_question_bank_release_items`, 승급 장부, 퇴역 manifest가 모두 세트 id로 움직인다. 물음 단위 파일은 저장할 때마다 세트로 다시 묶어야 하고, 그 묶는 규칙이 또 하나의 진실 원천이 된다.

세트 단위로 두면 기준서형 세트 대부분이 자연히 물음 하나짜리 파일이 되어 착상의 이득을 거의 그대로 얻는다.

## 4. 파일 배치

```
cpa_uploader/data/
  cpa_question_sets_v3.authoring.json      ← 생성물. 경로·바이트 유지
  sets/
    order.json                             ← 배열 순서. { version: 1, note, set_ids: [...] }. 사람이 고치는 유일한 순서 원천
    case/
      case-12-going-concern-20260920.json
      ...                                  (36개)
    standard/
      pilot-01-001.json
      std-points-20260914-ac4f0f2444b0.json
      ...                                  (307개)
```

- 파일 이름은 **세트 id + `.json`**이다. 다른 이름 규칙을 두지 않는다.
- `case/`·`standard/` 구분은 `learning-question-classifications.json`의 `question_style`에서 나온다. 혼합 세트는 계약상 존재하지 않으므로(현재 0건) 분류가 모호할 일이 없다. 새 세트가 혼합이면 생성기가 거절한다.
- 각 파일은 세트 객체 하나를 `JSON.stringify(set, null, 2) + "\n"`으로 담는다. `sets/` 바로 아래에는 `order.json`과 `README.md`만 둘 수 있고, 다른 파일이 있으면 생성기가 거절한다.

## 5. 가장 어려운 제약 — 순서

DB는 릴리스 항목마다 `position`을 저장하고, 판본 조회 RPC는 그 값이 저장 원문 배열에서의 위치(`source_position`)와 **같은지 확인**한다(`20260912060000_cpa_private_source_metadata.sql` 41~43행). 순서가 바뀌면 **과거 릴리스 전부의 위치 검사가 깨진다.**

현재 순서는 id 정렬이 아니라 **삽입 순서**다(파일럿 65개 → 이후 제작 순서 → 회차별 추가). 그래서:

- `sets/order.json`이 순서의 **유일한 원천**이다. 생성기는 이 목록 순서대로만 배열을 만든다.
- 이행 시점에 현재 정본의 배열 순서를 그대로 `order.json`에 적는다. **정렬하지 않는다.**
- 세트를 추가하면 `order.json` 끝에 붙이고, 퇴역시키면 목록에서 뺀다. 지금 `publish.mjs`의 배치 규칙("남는 세트의 상대 순서를 바꾸지 않고 새 세트를 뒤에 붙인다")과 같다.
- 생성기는 `order.json`의 항목 수와 `sets/**` 파일 수가 같고 서로 정확히 대응하는지 검사한다. 어긋나면 거절한다.

## 6. 생성기와 바이트 재현

```
npm run questions:v3:sets:build   # sets/** + order.json → authoring.json
npm run questions:v3:sets:check   # 생성 결과가 현재 authoring.json과 바이트 동일한지 확인(쓰기 없음)
npm run questions:v3:sets:split   # 이행용 1회. authoring.json → sets/**  + order.json
```

- `build`는 `order.json` 순서대로 파일을 읽어 배열로 합치고 `JSON.stringify(bank, null, 2) + "\n"`으로 쓴다.
- `check`는 CI·pre-commit용이다. **생성물과 원천이 어긋난 채 커밋되는 것을 막는다.**
- 바이트 재현은 실측으로 확인했다. 들여쓰기 2칸, 끝 개행 있음, 키 순서는 원본 객체의 순서를 그대로 따른다(`JSON.parse` → `JSON.stringify` 왕복이 키 순서를 보존한다).

## 7. 기존 기록과의 호환 — 이 설계의 핵심

**정본 파일이 같은 경로에 같은 바이트로 남는다.** 그래서:

- `analysis/reviews` 아래 **259개**의 과거 실행 기록·receipt·manifest가 가리키는 경로와 해시가 **그대로 유효**하다. 하나도 고치지 않는다.
- 정본을 **읽기만** 하는 살아 있는 코드 약 20개(`lib/questionV3Store.ts`, `next.config.ts`, `scripts/import-question-bank-v3.ts`, `cpa_uploader/wiki/scripts/*`, `analysis/coverage/build-coverage.mjs`, 테스트 8개 등)도 **고치지 않는다.**
- 고쳐야 할 것은 정본을 **쓰는** 쪽뿐이다.

| 고칠 대상 | 할 일 | 실제(2026-09-22) |
| --- | --- | --- |
| `cpa_uploader/questionBankPublication.ts`의 `writePublicationFiles` | 정본을 쓸 때 `sets/**`와 `order.json`도 함께 쓴다 | **여기 한 곳만 고쳤다.** 정본을 쓰는 모든 도구가 이 함수를 거치므로, 정본 파일 옆에 `sets/`가 있으면 세트 파일·순서 파일 쓰기와 퇴역 파일 삭제를 같은 원자적 쓰기에 더한다(`questionSetFiles.ts`의 `splitWritesForAuthoring`). 삭제(`content: null`)도 실패 시 되돌린다 |
| 회차별 `publication-*/publish.mjs --install` | 같은 원자적 쓰기에 세트 파일을 포함한다 | 변경 없음(위 함수를 거친다). 스테이지 사본(`tmp/…/authoring.json`)은 옆에 `sets/`가 없어 세트 파일을 만들지 않는다 |
| `cpa_uploader/correct_cpa_v3.ts`의 `publish` | 바뀐 세트 파일 하나만 다시 쓴다 | 변경 없음. 바이트가 같은 파일은 건너뛰므로 바뀐 세트 파일과 `order.json`만 쓴다 |
| `cpa_uploader/apply_cpa_v3_review.ts`·`generate_cpa_v3.ts` | 쓰기 경로가 있으면 같은 규칙을 따른다 | 변경 없음. 정본을 직접 쓰는 경로는 `sets:check`가 어긋남을 잡는다 |
| `.githooks/pre-commit` | `sets:check`를 더한다 | Gate 1/5로 넣었다(가장 빠른 검사라 맨 앞) |

과거 회차의 `publish.mjs` 사본들은 **고치지 않는다.** 이미 실행이 끝났고 그 바이트가 기록에 고정되어 있다.

## 8. 이행 절차

1. `sets:split`을 한 번 실행해 `sets/**`와 `order.json`을 만든다. 정본 파일은 건드리지 않는다.
2. `sets:check`로 **재생성 결과가 현재 정본과 바이트 동일**함을 확인한다. 다르면 여기서 멈춘다.
3. 생성기·검사기와 `sets/**`를 커밋한다. 이 커밋에서 정본 파일은 **변경되지 않는다**(diff 0줄). 되돌리기 쉬운 지점이다.
4. 쓰기 경로(7절 표)를 고치고 테스트를 더한다.
5. pre-commit에 `sets:check`를 넣는다.
6. 다음 회차 설치를 새 경로로 한 번 돌려 본다. 그 회차의 정본 diff가 **바뀐 세트만큼만** 나오는지 확인한다.

승급·설치가 도는 중에는 이행하지 않는다. 게이트가 정본·장부 불변을 감시하므로 겹치면 실패한다.

## 8-1. 세트 파일을 직접 고쳤을 때

세트 파일을 손으로 고쳤으면 `npm run questions:v3:sets:build`로 정본을 다시 만든 뒤 `npm run questions:v3:validate:authoring`을 실행한다. 게시된 세트의 내용을 바꿨다면 승급 장부의 내용 해시와 어긋나 검증이 거절하므로, 그런 변경은 여전히 [수정 패치](../cpa_uploader/corrections/README.md)나 제작 경로의 검수·승급 계약을 따른다. 파일을 고쳤다는 것만으로 검수가 되지 않는다.

## 9. 위험

- **순서 사고**: `order.json`을 정렬하거나 다시 매기면 과거 릴리스의 위치 검사가 전부 깨진다. 생성기에 "정렬 금지" 주석과 검사를 함께 둔다.
- **두 진실 원천**: 생성물을 손으로 고치면 어긋난다. `sets:check`를 pre-commit에 넣어 막는다.
- **파일 수**: 343개가 새로 생긴다. git은 문제없지만 한 번의 커밋 diff가 커 보인다. 3단계에서 정본 diff가 0줄인 것이 그 상쇄다.
- **혼합 세트**: 계약상 없지만(현재 0건) 생성기가 만나면 거절하도록 해 조용히 잘못 배치되지 않게 한다.

## 10. 이 설계에 없는 것

승급 장부(12 MB) 분리, 판본 조회 RPC 최적화, 게이트·검증 시간 단축은 포함하지 않는다. 각각 별도 설계가 필요하며, 그중 RPC는 [판본 조회 RPC 최적화](판본-조회-RPC-최적화-2026-09-21.md)에 방안을 정리해 두었다.

## 11. 이행 기록 (2026-09-22)

- 구현: `cpa_uploader/questionSetFiles.ts`(분리·재생성·검사·쓰기 계획), `scripts/manage-question-set-files.ts`(`split`·`build`·`check`), `writePublicationFiles`의 fan-out과 삭제 지원, `tests/questionSetFiles.test.ts`(저장소 게이트 1건 + 격리 5건), pre-commit Gate 1/5.
- `split` 1회 실행: 정본 343세트를 `sets/case/` 36개·`sets/standard/` 307개와 `order.json`으로 나눴고, 재생성 결과가 정본과 **바이트 동일**함을 확인했다. 정본 파일은 바뀌지 않았다(diff 0줄).
- 배치 디렉터리는 `learning-question-classification-review.json`의 물음별 `question_style`로 정했다. 세트 46개는 원문에 `question_style`이 없어 분류 입력이 유일한 근거였다.
- 이 설계가 풀지 않는 것(1절 표)은 그대로다. 회차별 스크립트 복사를 없애는 일은 [문항 수정 패치 운영](문항-수정-패치-운영.md)의 통째 교체 명세(2026-09-22)가 단독 갱신을, 병합용 공용 도구가 병합·분리를 맡는다.
