# 회계감사 문제·물음 검증과 수정

문항 내용과 실제 채점의 일치를 확인한다. ‘검토해줘’는 조사·수정안, ‘검증하고 수정해줘’는 허용된 로컬 수정과 재검증까지 수행한다. 이미 승인된 수정은 다시 묻지 않는다. 계획 요청을 제품 수정으로, 스킬 호출을 배포·운영 DB 변경으로 확대하지 않는다.

[제작 스킬](../audit-question-author/SKILL.md)에서 이어지는 신규 초안 검증은 기본 제작 범위에 포함된다. 이 경우 의미검수·실제 모델 채점과 초안의 불일치 수정·재채점까지 수행하며 별도의 검토 요청을 기다리지 않는다. 사용자의 초안 한정·모델 호출 제한은 그대로 적용한다.

이 파일이 Claude·Codex 공통 본문이다. 아래 코드 경로는 작업 중인 `audit_say` 저장소 루트 기준이다. [회귀 사례 지침](references/regression-cases.md)은 실제 채점 또는 채점 계약을 검토할 때 읽는다.

현재 프로젝트의 기본 경로는 [비용 통제 검증 지침](references/cost-controlled-verification.md)이다. agent의 실제 내용 대조와 별도 유료 API 의미검수를 구분하고, Luna의 대표 답안 채점으로 물음별 ±1점·검증 답안 95% 목표를 확인한다. 아래 전통적 criterion별 모델 receipt·전수 반례 경로는 사용자가 그 강도를 명시하거나 위험에 맞춰 선택한 경우에 적용한다. 옛 실행 스크립트가 더 많은 호출을 요구한다는 이유로 새 정책보다 우선하지 않는다.

원문·판본·인용 또는 출처 패킷을 대조할 때는 [공통 출처 검증 지침](references/source-evidence.md)을 읽는다. wiki 기반 자료와 실제 검증에 사용한 출처는 `cpa_uploader/raw/`의 수집 기록에서 추적하고 누락 자료는 미확보로 남긴다. 출처 정리만 요청된 경우 원자료 수집·보존·연결 검사를 수행하며 이를 모델 채점이나 게시로 확대하지 않는다.

## 유형별 검증 경로

사용자가 스킬 이름을 쓰지 않아도 유형 구분·주제 대응·배점 타당성·부분정답·문항 검증 요청에 적용한다. 새 초안도 검증 단계에서는 이 스킬을 따른다. 저장된 유형을 그대로 믿지 말고 발문·사실·답안·criterion으로 재판정한 뒤 해당 경로를 적용한다.

| 경로 | 확인할 내용 | 잘못된 경우의 처리 |
| --- | --- | --- |
| 기준서형 물음 검증 | 부모 사실·다른 물음 없이 독립 발문으로 충분한지, 일반 기준서 답안으로 만점 가능한지, 숨은 사례 조건이 없는지 | 독립 발문 보완 또는 사례형 재분류 필요성을 기록하고 요청 범위의 후속 판본으로 수정 |
| 사례형 문제·물음 검증 | 각 사례 적용 점수에 필요한 사실이 부모에 있는지, 사실과 답안 적용이 맞는지, 일반론만으로 같은 만점을 얻는지, 소속 물음에 기준서형이 섞였는지 | 필요한 사실·적용 criterion 보완 또는 기준서형 분리; 사례 검색·제출에는 소속 사례형 물음 전체 유지 |

분류만 검토하는 요청은 분류 근거·주제·부모/독립 발문을 대조하고 그 범위로 보고한다. 원문이나 실제 채점 입력을 바꾸지 않는 메타데이터 검토를 신규 제작·실제 API 채점으로 확대하지 않는다. 발문·사실·criterion·배점 또는 실제 전달되는 채점 입력이 달라지면 영향받는 의미검수·채점 검증을 수행하되 사용자의 호출 제한을 따른다. 새 사실관계·새 요구를 제작할 필요가 있고 허용된 범위이면 [제작 스킬](../audit-question-author/SKILL.md)을 추가한다.

## 1. 범위와 현행 계약

- 대상 ID·발문·답안·criterion·배점·데이터/코드 해시를 확보한다. 전수 검토는 모든 대상 물음·criterion을 장부에 포함한다. 주제별로 나눠 기록하고 표본 실측을 전수 실측이라고 표현하지 않는다. 개수·총점은 현재 자료에서 계산한다.
- `cpa_uploader/wiki/_meta/authoring-dashboard.md`와 `cpa_uploader/analysis/coverage/README.md`에서 현재 은행·초안·검수 자료와 연결 레지스트리의 입력 해시를 확인한다. 날짜별 보고서는 당시 기록이며 현재 검수·편입 상태는 현행 데이터와 대조한다. 자동 인용 연결을 의미상 출제 범위의 승인으로 해석하지 않는다.
- `docs/plans/주제-01-03-검토에-따른-수정-결정.md`, `cpa_uploader/wiki/question-generation/question-design.md`, `question-output-schema.md`, 필요한 `topics/topic-XX-design.md`와 해당 주제 보고서를 읽는다. 마지막 세 경로는 `question-generation/` 기준이다. 분리된 주제 규칙을 공통 문서의 옛 제목에서 찾지 않는다.
- 과거 주제별 Markdown 보고서는 `docs/archive/과거-검토-증거/reports/question-review-2027/`, 대응 JSON·채점 사례·출처 증거는 `cpa_uploader/analysis/reviews/question-review-2027/`에서 읽는다. 여러 문항·주제에 걸친 후속 검토 자료는 `cpa_uploader/analysis/reviews/`, 개별 제작 배치의 계획·QA·receipt는 해당 `cpa_uploader/drafts/` 배치에 둔다. 세부 소유권은 `docs/출제-검토-자료-관리.md`를 따른다.
- **확정 정책 / 현재 코드·데이터 / 과거 평가 계약**을 구분한다. 후속 사용자 결정을 과거 보고서의 답변 대기·상한·감점 제안보다 우선한다. 엔진이 정책을 이미 구현했다고 가정하지 않는다.
- [물음별 학습 단위 계약](../../../docs/물음별-학습-단위와-분류-계약.md)을 읽고 원문 세트·물음 판본과 학습 분류 판본을 구분한다. 새 문항의 `question_style`·`topic_ids`와 과거 문항의 sidecar·봉인 메타데이터를 함께 확인하되 원문에 메타데이터가 없다는 이유만으로 과거 바이트·receipt를 고치지 않는다.
- 적용 연도·범위가 정답을 바꿀 정도로 미정이면 질문하며 독립 조사는 계속한다. 기존 2027년 배치의 2026년 기준 동일 적용은 그 배치의 가정이다. 새 작업 전체에 확장하지 않는다. 새로운 현행성·시행일 판단은 공식 자료로 확인하고 KGA 220의 해당 판본은 `docs/archive/과거-검토-증거/reports/question-review-2027/개정-감사기준서-220-시행일-별도-기록.md`도 대조한다.

## 2. 원문·발문·모범답안·배점 대조

물음마다 **주어진 사실 → 실제 요구 → 모범답안 명제 → criterion → 직접 근거**를 양방향으로 대조한다. 독립된 상황인지, 시점·주체·조건이 충분한지, 결론을 지문에 이미 주었는지 확인한다.

[공통 배점 계약](../../../docs/물음별-학습-단위와-분류-계약.md#배점과-물음별-타당성)을 읽고 열거 요소별 득점, 서술의 독립 의미 단위별 부분점수, 판단·근거의 독립 득점을 검토한다. 물음마다 최소 충분 답안과 서술·추론 부담, 독립 요구 수, 유사한 물음의 배점을 비교해 **유지/조정/분리와 이유**를 남긴다. 과도한 요구 묶음·중복 배점·언어 조각 분해·숨은 요건을 따로 확인한다. 총점 계산 통과만으로 배점 타당성 검토를 끝내지 않는다.

- 같은 대조로 사례 사실과 연계해야 답할 수 있는지, 기준서 내용만으로 독립 풀이가 가능한지 판단한다. 물음별 주제는 실제 요구내용으로 확인한다. 기준서형의 독립 발문이 요구·정답을 바꾸지 않는지와 사례형의 부모 사실이 충분한지를 학습 단위 계약에 따라 검토한다.
- 모든 물음의 계약은 `selection={type:'all',n:null}`, `constraints={ordered:false,max_entries:null,overflow_policy:'none'}`이다. 일부 선택·앞 N개·최고 N개 제한을 없애되 의도된 발문 범위와 절차의 의미상 선후관계를 보존한다. 문장·번호·줄바꿈 개수로 정답을 자르지 않는다.
- 독립 명제는 기본 1점이며 소수 partial을 허용하지 않는다. 일부 criterion을 충족한 점수는 유지한다. 정수 가중치가 있다면 별도 계약을 확인한다. 옛 세트 8점 제한에 맞춰 독립 요구를 합치거나 삭제하지 않는다.
- 명칭을 물었으면 명칭으로 점수를 준다. 정의·이유·조치를 요구한 criterion은 해당 의미를 확인한다. 발문에 없는 요건·주어진 사실의 반복·해설의 부가 지식에 숨은 배점을 하지 않는다.
- 판단과 근거의 분리/결합 계약을 확인한다. 요구 조치나 이유에서 결론이 분명하면 결론 문구를 따로 쓰지 않아도 판단을 인정한다. 명시적 반대 결론은 판단 0점이며, 별도로 충족한 근거는 해당 criterion 계약에 따른다.
- 하나의 문장이 여러 독립 명제를 충족하면 동일 인용을 허용한다. 같은 사실의 표현만 다른 중복 배점은 제거한다. requirement 공유만으로 criterion을 합치지 않는다.
- 조건·부정·대상·그리고/또는·대안 선택·법규상 예외·기간·보고 상대방/시점/서면 여부를 보존한다. 여러 대안을 모두 서술하는 답안과 실제로 모든 대안을 수행해야 한다는 주장을 구분한다. 명칭과 정의, 설계·실행과 운영효과성, 고려 가능성과 의무를 혼동하지 않는다.
- 공식 원문의 본문·하위 항목·적용자료·예외·의존 문단과 적용 판본을 확인한다. 요약·해설·wiki와 로컬 인용 실존만으로 공식 내용의 정확성을 확정하지 않는다. 찾지 못한 자료·판본은 미확인으로 남긴다.
- 인용 윤문·합성·범위 명료화의 실제 처리와 `source_fidelity`를 대조하고 인용 문자열 SHA-256과 파일 해시를 구분한다. `source_refs[].page`의 `KGA NNN` 분류, `classification.standards`, 출처 파일의 `#`~`### KGA NNN:` 제목 구간은 `cpa_uploader/questionBankPublication.ts` 계약을 확인한다. PDF 쪽수·문단은 `title`, `source_span`, 출처 장부와 대조한다.

빈도나 미출제 주장을 포함한 문항이면 `cpa_uploader/wiki/question-generation/question-elements.md`와 `cpa_uploader/analysis/question-elements/README.md`, `deduplication.md`, `question-elements.json`을 읽는다. 요소 ID와 원발문·원출제 식별까지 확인하며 재수록만 제외하고 서로 다른 실제 출제는 유지한다. 기출·모의·연습 수를 구분하고 직접 요구와 인접 요구의 빈도를 바꿔 쓰지 않는다. 과거 공백 보고서를 현재 정본·진행 중 초안과 재대조한다. 0회·인용 연결 없음·낮은 문구 유사도를 미출제 확정으로 보고하지 않는다.

요소↔기준서 요구↔문항 관계를 수정하면 `cpa_uploader/analysis/coverage/links.json`에 기존 ID·관계·근거·검토 상태·확인 당시 해시를 기록한다. 자동 생성 `registry.json`은 직접 고치지 않는다. 생성 결과의 `freshness`, `changed_inputs`, `effective_review_status`로 현재 재검토 대상을 확인한다. `stale`이면 이전 `review_status=reviewed`만으로 현재 관계를 확인 완료로 판단하지 않고, 해시만 갱신해 검토를 대신하지 않는다. 은행 밖 대상은 coverage README의 초안 범위·파일 계약으로 대조하며, 과거 관계 가져오기나 재생성 성공만으로 의미검수·사람 확인 상태를 올리지 않는다.

진행 중인 초안은 `cpa_uploader/drafts`와 사용자가 지정한 별도 폴더도 조사한다. `cpa_uploader/questionDraftInventory.ts`의 `readPendingDrafts` 기본 탐색은 `cpa_uploader/data`이며 추가 폴더는 `extraDirectory`로 전달해야 한다.

## 3. 실제 채점과 회귀 확인

학습 유형별 검증과 공통 배점 검증의 결과를 구분해 기록한다. 기준서형은 사실 없이 답한 완전 정답을, 사례형은 일반론만 답한 경우와 실제 사실에 맞게 적용한 경우를 비교한다. 분할한 기준은 기존 첫 기준을 포함해 각각 기대값을 다시 정하고, 한쪽만 맞은 양방향 부분정답으로 정수 점수가 보존되는지 확인한다. 상세 사례는 [회귀 지침](references/regression-cases.md)을 따른다.

실측이 포함되면 `lib/questionV3Grading.ts`, 관련 API·`package.json`에서 현재 경로를 확인한다. 저장 모범답안과 합성 답안을 사용하며 실제 사용자 개인정보는 넣지 않는다. 모델·설정·캐시 여부·코드/데이터 버전을 기록한다.

- 독립 풀이·부분 세트 제출을 다루면 학습 단위 계약의 v2 선택·답안·분류 판본 결속과 선택 범위의 채점·최대점수·경험치·복습을 확인한다. 주제는 검색 필터이므로 검색된 사례형 단위의 물음 전체를 보여 주고 풀이 범위를 자르지 않는지 확인한다. 기존 v1 전체 세트, 회원 상태 검증·서명키 호환과 과거 기록도 함께 보존한다. 분류 변경만으로 이전 실측의 재사용을 자동 승인하지 않는다.
- criterion마다 완전 답안·허용 표현·한 명제 누락·반대 의미·조건 경계를 내용상 검토하고 모든 물음의 빈 답안 경로를 확인한다. 실제 API에는 비용 통제 지침에 따라 대표 사례를 선정한다. 열거형의 역순·한 문장·정상 명칭 나열, 판단형의 함축 결론·명시적 반대 결론·근거 누락 중 위험에 해당하는 사례를 추가한다. 기대값은 원문·정책에서 먼저 정한다.
- 누락은 남은 답안 전체로 판정한다. 결론 문장 삭제 후 이유가 같은 판단을 함축하면 판단 누락 사례가 아니다. 실제 적용 조건을 바꾼 경계 사례와 단순 반대 문장을 구분한다.
- 원시 criterion·근거 ID 판정 → ID·누락 검증과 답안 원문 인용 복원 → 보안 의심의 독립 재확인 → 최종 합산을 분리해 실패 위치를 찾는다. 잘못된 ID를 순서·유사 문구로 추정 보정하지 않는다. 저장 모범답안의 만점, 빈 답안 0점, 과도한 중복 감점·정상 명칭 나열의 보안 오탐을 확인한다. 정상 사례는 기대 0점과 같아도 물음별 보안 오탐이 있으면 통과가 아니다.
- 실행 오류를 답안 오답과 구분한다. 모델 전송·응답 오류의 제한 재시도와 기록용 콜백 실패를 분리하고, 기록 코드가 판정이나 점수를 변경하지 않는지 확인한다. 상세 오류 경계와 회귀 사례는 [회귀 지침](references/regression-cases.md)을 따른다.
- 실제 모델 호출, 캐시 재생, mock, 작성자의 기대 판정 재생을 구분한다. `applyQuestionSetJudgment`에 작성자 기대값을 넣은 QA는 합산 검사이며 모델 의미 판정의 정확도 측정이나 정식 검수 receipt가 아니다. 의미검수·실제 채점·사람 확인의 증거를 각각 기록한다.
- 허용한 ±1점 편차는 별도 수락 결과로 기록하고 추가 반복하지 않는다. 허용 범위를 벗어난 결과는 원인을 먼저 조사하고 필요한 수정·표적 재검사만 수행한다. 총 3회 관측이 필요한 변동 조사도 목적·예산을 정해 선택하며 모든 불일치에 자동 적용하지 않는다. 실행 환경·키·예산 때문에 못 했다면 정적 확인과 미실측을 구분한다. 모델의 오판에 맞춰 정답이나 기대값을 바꾸지 않는다.
- 불일치는 원문·발문·모범답안·criterion·기대값의 문제인지, 모델 의미 판정·인용 검증·보안 보정·합산의 문제인지 조사한다. 수정 권한이 있는 작업에서는 근거가 확인된 발문·답안·채점 기준을 함께 고치고 동일 반례와 영향받는 정상·부분 답안 사례를 최종 버전으로 재채점한다. 사례를 더 명시적인 표현으로 교체해도 유효한 원답안·경계 반례를 회귀 묶음에 남긴다. 기대값 자체가 잘못되었으면 원문에 따른 정정 근거와 이전 값을 보존한다. 모델 결과에 맞춘 기대값 변경이나 통과할 때까지의 무근거 재호출은 하지 않는다.
- 반복 실측 후에도 원인을 해결하지 못했거나 실행 장애·사용자 예산에 도달하면 잔여 실패와 재개 조건을 남기고 검증 미완료로 보고한다. 공통 채점 코드의 결함은 영향 범위와 관련 회귀 검사를 확인하여 처리하며 개별 초안만 통과시키려 정답 명제를 삭제하지 않는다.

## 4. 초안 의미검수와 승급 근거

비용 통제 경로에서는 모든 대상 물음의 실제 agent 내용 검토 장부와 대표 답안의 실제 채점 증거를 별도 계약으로 수락한다. agent 검토를 모델 API 호출이나 사람 확인으로 표시하지 않는다. 사용자가 이 검증 경로와 검증 후 게시·DB 반영을 승인했다면 그 범위 안에서 진행하며, 과거의 별도 사람 확인 절차를 기계적으로 재요청하지 않는다. 새 경로가 아직 코드에 없다면 기존 상태·검수 receipt를 꾸며 통과시키지 말고 명시적인 증거 형상과 검증·승급 경로를 구현한다. 아래 모델 receipt 절차의 기존 기록·엄격 검사 경로는 보존한다.

초안의 정식 검수 또는 승급을 다루면 `cpa_uploader/wiki/question-generation/source-authoring-design.md`, `cpa_uploader/review_question_draft_v3.ts`, `questionSemanticReview.ts`, `promote_cpa_v3.ts`를 읽는다. 마지막 세 파일은 `cpa_uploader/` 기준이다. 현재 인자·출력·API 호출 여부를 확인한 뒤 실행한다.

- 계획 `ready`, 문항 `needs_review`, 의미검수 pass, 실제 사례 채점 완료, 사람 검수, verified/published를 구분한다. 자동으로 동등한 상태로 올리지 않는다.
- sidecar 자동 탐색은 `draft.json.authoring-plan.json` / `draft.json.source-packet.json`이다. 수동 배치처럼 다른 이름이면 `--plan <실제 경로>`와 필요한 `--packet <실제 경로>`를 명시한다. 생성 당시 `출제 계획 해시:`를 기록한 문항의 패킷 필수 계약을 확인한다. 그 표시가 없는 수동 초안의 패킷 부재를 일괄 형식 결함으로 판정하지 않는다.
- 모델 의미검수와 실제 사례 채점은 `review_question_draft_v3.ts --file <draft.json> --plan <plan.json> --grade-cases --output <review.json>` 경로를 사용한다. 생성기 패킷이 있으면 전달한다. 모델·키는 현재 환경 설정을 따르며 특정 모델명을 스킬에 고정하지 않는다.
- 수동 의미 대조는 `--manual-template`로 양식을 만들고 모든 단위·사례·실인용·판정 근거를 채운 다음 `--manual-input <template.json> --description <실제 확인 방법>`으로 기록한다. 양식만 만든 것을 검수로 보고하지 않는다. 작성자 자체 QA와 독립 검토자·사람 확인을 구분한다.
- 의미검수만 완료된 receipt의 실제 채점은 `--review-input <semantic-review.json> --grade-cases --output <다른 경로>`로 실행한다. `grading.status=not_run`이면 실제 채점 완료가 아니다. 의미검수의 `execution.transport`와 사례 채점의 `grading.transport`를 각각 확인한다. 신규 수락에서 모델 의미검수는 `execution.transport=model`, 실제 채점은 `grading.transport=model`이어야 한다. 주입 응답 또는 transport 미기록 모델 의미검수에 실제 채점만 붙여 새 검수 근거로 사용하지 않는다. 과거 기록은 보존하고 필요한 실제 의미검수를 새로 수행한다.
- `<output>.chunks.jsonl`과 `<output>.grading.jsonl`에 성공·불일치·실패의 중간 증거를 보존한다. 기존 로그를 덮어쓰지 않도록 재실행에는 새 출력 경로를 쓴다. 부분 로그를 완료 receipt로 표시하지 않는다. 이 보존·검사 절차의 상세는 회귀 지침을 따른다.
- 검수 대상·계획·패킷·출처·비교 은행·배치가 바뀌면 현행 해시 계약에 따라 새 검수 증거를 기록한다. 사례·채점 코드가 바뀌면 실제 사례 채점도 갱신한다. 이전 receipt·입력 해시·실행 결과는 보존하며 옛 캐시·장부로 새 내용의 검수 완료를 주장하지 않는다.
- 정본 반영·승급이 요청 범위이면 선택한 검증 경로의 통과 증거와 실제 사용자 승인 범위를 승급 도구에 전달한다. 전통적 사람 확인 경로를 사용했다면 실제 사람 검수 근거를 기록한다. 비용 통제 경로의 agent 검토·게시 승인과 사람의 내용 확인은 별도 필드로 기록한다. 이미 verified/published인 문항을 수정했다면 재검수 이력을 추가하며 과거 장부를 삭제하지 않는다.

## 5. 수정·검증·보고

- 먼저 관찰한 결함·근거·반례·영향과 수정 범위를 기록한다. 수정 요청이면 허용된 파일을 고치고 동일 반례를 재검증한다. 수정안을 제시했다는 이유만으로 실제 수정 완료라고 보고하지 않는다.
- 발문/답안/criterion의 문제는 함께 맞추고 배점·범위 변화의 근거를 남긴다. 채점 엔진 문제를 숨기려고 정답 명제를 삭제하거나 학생에게 불필요한 문장 분리를 요구하지 않는다. 오탈자 수정에 전체 엔진·UI·DB 개편을 붙이지 않는다.
- 기존 ID 문항 수정의 형상·인용은 `npx tsx cpa_uploader/validate_draft_v3.ts --file <draft.json>`로 검사한다. 같은 ID의 자기 충돌을 만들 `--against-bank`를 무조건 붙이지 않는다. 신규 ID 편입이면 `--against-bank`와 배치 중복 확인을 사용한다.
- 편입·교체 결과는 정본을 쓰기 전 메모리에서 `validateAuthoringBank`로 검사한다. 교체 대상의 옛 버전은 빼고 새 버전을 넣는다. 정본 변경 후 `npm run questions:v3:validate:authoring`, 관련 타입 검사·테스트를 수행한다. 공개본/암호화본을 생성한 뒤 `npm run questions:v3:validate`로 전체 산출물을 확인한다.
- 출제 정책·출처·검수 절차가 바뀌면 wiki `SCHEMA.md`와 관련 수동 문서를 갱신하고 생성 대상은 생성기/입력에서 재생성한다. 연결 분석 입력이 달라지면 `npm run analysis:build`와 `npm run analysis:check`, wiki 입력이 달라지면 `npm run wiki:build`와 `npm run wiki:check`를 수행한다. 원자료는 빌드 편의로 바꾸지 않는다. `log.md`에 이유와 결과를 남기고 관련 변경이 없으면 형식적인 wiki 수정은 하지 않는다.
- 변경 범위에 맞는 검사를 수행한다. 채점·보안·합산 코드 변경에는 해당 회귀 검사를, UI/API/DB 변경까지 포함되면 해당 사용자 경로와 비밀정보 비노출을 확인한다. 이미 통과한 검사는 새 변경·실패·미해결 우려가 있을 때만 확대한다.
- 최종 결과는 **발견 / 수정 / 실제 검증 / 미검증·미해결**을 구분한다. ID·파일·근거·배점 변화·실측 범위를 제시하고, 오류 0개가 기준서 정확성·전수 모델 품질·게시 완료를 뜻하지 않음을 결과에 맞게 설명한다.
