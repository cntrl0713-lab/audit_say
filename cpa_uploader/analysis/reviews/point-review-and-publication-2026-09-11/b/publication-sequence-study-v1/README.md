# 비교은행 변경과 순차 검수 기록의 계약 조사

일부 세트의 변경 때문에 **이미 적법하게 기록한 다른 세트의 승인을 전부 다시 실측할 필요는 없다.** 현행 코드는 신규 수락과 과거 기록 검증을 의도적으로 구분한다. 그러나 **과거 은행의 pass receipt를 아직 신규 수락하지 않은 상태에서 변경된 은행에 바로 승급하는 것은 거부된다.** 최초 은행에서 실제 검수·실제 채점·사람 확인을 마치고 그 버전의 승인을 먼저 기록해야 한다.

이번 실제 v6 후보는 별도 제약이 있다. `published` 34개, `needs_review` 119개 중 기존 수정 70개에는 원 승급 장부가 있다. 원 장부를 그대로 쓰면 70개 모두 `승급 장부와 needs_review 상태가 불일치합니다`에 걸린다. 따라서 아래 일반 순차 방식이 가능하다는 결과를 **현재 119개 후보에 기존 CLI만으로 즉시 적용 가능하다**고 해석하면 안 된다. 원 기록을 지우거나 수정된 구문을 예전 검수로 승인했다고 간주하는 우회도 제안하지 않는다.

## 실제 코드 계약

| 확인 지점 | 실제 동작과 의미 |
| --- | --- |
| `questionReviewIdentity.ts:9` | 검수 내용 해시에서 `status`와 `verification.review_status` 두 필드만 제외한다. 발문·정답·점수·출처·verification notes 등 다른 변경은 내용 변경이다. |
| `questionSemanticReview.ts:175` | 비교은행 해시는 대상 자신의 ID를 제외하고 ID로 정렬한 동료 세트의 `id/content_hash` 목록이다. 은행 파일 전체 바이트 SHA와 다른 값이다. 상태만 승급하거나 배열 순서를 바꾸면 비교은행 해시는 유지되지만 동료 내용 수정·추가·삭제는 바꾼다. |
| `questionSemanticReview.ts:316` | `validateSemanticReviewReceipt`는 신규 수락 시 현재 은행과 receipt의 비교은행 해시를 대조한다. 이전 은행의 receipt를 수정 은행에 신규 수락할 수 없다. |
| `questionSemanticReview.ts:320` | `gradeSemanticReviewReceipt`도 먼저 동일한 현재 은행 검사를 한다. 의미검수만 통과하고 생성 사례의 실제 채점이 미완료라면 은행 전환 전에 채점까지 완료해야 한다. 별도 작성자 QA 성공만으로 이 receipt의 `grading`을 대체할 수 없다. |
| `questionSemanticReview.ts:331` | `validateRecordedSemanticReview`는 현재 동료은행을 비교하지 않는다. 그 세트 내용, 실제 출처파일, 알려진 출처 권위·판본 metadata, 계획/packet의 유효성, receipt 무결성·pass, 사례 및 기록한 원시 판정의 현재 합산 재현은 계속 검사한다. |
| `questionReviewGrading.ts:146` | 과거 기록은 이전 채점 모델·코드 해시 자체를 보존하되 원시 판정·기대·결과의 재현을 계속 요구한다. 신규 수락은 현재 채점 모델·코드 해시와 실제 model transport도 요구한다. |
| `promote_cpa_v3.ts:40–106` | 전체 은행 형상 → 전체 기존 장부 → 이번 세트의 신규 receipt → 최종 전체 장부를 차례로 확인한 뒤 은행/장부를 함께 쓴다. 실제 `--evidence`가 필요하며 이 연구는 그 근거를 만들지 않았다. |
| `questionBankPublication.ts:214–245` | `needs_review` 세트에는 기존 항목이 없어야 한다. 이미 승인한 세트의 수정은 명시적 `--reverify`로 다루며, pending 예외는 이번 재검수 대상 ID에만 적용된다. 다른 수정 승인 세트까지 예외가 확장되지 않는다. |
| `promote_cpa_v3.ts:104`, `compile-question-bank-v3.ts:22` | 게시 단계와 공개본 컴파일은 전체 은행이 published인 상태를 요구한다. 일부만 verified로 준비할 수 있는 것과 일부만 운영 게시할 수 있는 것은 다르다. |

실제 행 위치와 파일 SHA는 [checks.json](checks.json)의 코드 스냅샷에 묶었다. 의미검수·채점의 실제 API provenance 및 런타임 고정은 외부 execution manifest/worker 증거도 필요하다. receipt의 필드만 보고 실제 모델 호출을 했다고 추정하지 않는다.

## 가능한 순서와 반드시 남길 근거

1. 초기 은행 B0의 문항·출처·계획·코드·모델을 고정하고 전체 동료를 포함해 검수한다. 각 통과 세트는 의미검수 pass와 그 receipt의 실제 생성 사례 채점 pass를 모두 갖춘다. 요청된 작성자 QA와 불일치 조사도 따로 마친다.
2. 실제 사람 확인을 받은 통과 집합 P0를 **아직 B0가 해당 스테이징의 비교은행일 때** 검수 기록한다. 기록에는 원 receipt 전체와 해시·내용 해시·원 실행 증거를 그대로 보존한다. 상태 두 필드만 바뀌므로 P0의 순차 수락은 서로의 은행 해시를 바꾸지 않는다.
3. 미통과/미승인 집합 F만 후속 B1으로 고친다. 승인된 P0의 내용·출처·계획·metadata는 바꾸지 않는다. 이후 F를 B1 전체 동료와 대조해 새로 검수·실제 채점하고 사람 확인 후 추가 기록한다. F의 신규 검수는 앞서 승인한 P0와의 중복·범위 관계도 다시 확인해야 한다.
4. P0는 `validateRecordedSemanticReview`, F의 새 수락은 `validateSemanticReviewReceipt`로 검사한다. P0의 receipt `bank_hash`, 실행시각, 모델, source hash를 B1 값으로 새로 써 넣지 않는다. 서로 다른 epoch의 유효 기록은 한 최종 장부에 공존할 수 있다.
5. 후속 F 변경이 P0의 정답·경계·공유 출처 등 자체 계약에도 영향을 주면 P0도 영향 범위에 넣는다. 과거 기록 함수가 동료은행을 무시한다는 사실은 의미상 영향 검토를 면제하지 않는다. 전체 준비가 완료된 뒤 최종 은행/분류/게시·컴파일/DB 경로를 검사한다.

새 draft만 남고 기존 승인본이 모두 유효한 은행에서는 이 순서가 현재 CLI와 일치한다. CLI에는 별도 비교은행 인자가 없고 `CPA_QUESTION_V3_AUTHORING_PATH`의 실제 스테이징 은행을 사용한다. 스테이징 authoring/ledger/public/encrypted 경로는 모두 서로 달라야 하며 원본·DB 경로와 분리해야 한다. 큰 은행의 신규 검증에는 기존 실행과 동일하게 `CPA_REVIEW_INPUT_MAX_CHARS=500000` 설정이 필요할 수 있다. 이 연구에서는 CLI를 호출하지 않았다.

## 이번 기존 70개 수정의 추가 제약

- v6 실제 후보와 원 장부를 읽기 전용으로 대조하니 오류 70개가 모두 기존 수정 ID의 `needs_review`/과거 장부 충돌이었다. 상세 ID는 [checks.json](checks.json)의 `real_candidate_diagnosis`에 있다.
- 후보의 상태를 원 published/verified로 복구하는 것만으로도 일반적인 해결은 되지 않는다. 해시로 묶인 과거 승인 내용이 바뀌었다면 재검수가 필요하고, `--reverify P0`는 다른 수정 승인 세트 F의 해시 불일치를 면제하지 않는다. `--reverify P0,F`로 늘리면 F의 유효 receipt도 이번 호출에서 필요하다.
- 원 장부를 없애거나 기존 항목을 빼서 needs_review의 첫 승급처럼 만드는 것은 현재 이력 계약의 해결책으로 권고하지 않는다. 백필 옵션도 신규 소급 승인에 사용할 수 없다. 사람 확인 전 pass receipt를 기승인 기록으로 승격시켜 bank 검사를 건너뛰어서도 안 된다.
- **공통 코드 변경 없이 엄격한 현재 승급 경로만 사용하려면**, 현재 장부와 일치하는 초기 스테이징 구성이 선행되어야 한다. 이미 변경된 모든 기승인 대상 때문에 전체 선검사가 실패하면 해당 재검수 cohort의 근거가 모두 갖춰질 때까지 일부 승급을 보류해야 한다. 이 경우 아직 수락하지 않은 receipt의 비교은행 변경 문제는 남는다.
- 불필요한 반복을 줄이려면 후속 구현으로 **명시적으로 고정한 후보 버전의 부분 수락을 보존하는 스테이징 거래**를 검토할 수 있다. 원 장부를 불변 baseline으로 유지하고, 실제 이번 승인 ID와 아직 재검수 대기 중인 변경 ID를 별도로 봉인하며, 대기 ID를 승인·게시 가능한 상태로 취급하지 않는 계약이 필요하다. 선검사·후검사 모두 대기 범위를 검사하고, 최종 게시/컴파일에는 대기 0개를 강제해야 한다. 이는 현행 `--reverify` 옵션에 이미 있는 기능이 아니다. 이 연구에서는 helper/공통 코드/장부를 구현하거나 바꾸지 않았다.

## 로컬 fixture 결과

[study.mjs](study.mjs)를 실행해 33개 확인이 통과했다. 그중 보호 파일 바이트 검사 10개를 제외한 23개는 수락·이력·모델·출처·상태 및 실제 후보 진단의 경계 검사다.

- 처음 A 수락 → 미승인 B 수정 → B의 새 receipt 수락 → 서로 다른 비교은행의 A/B 기록 동시 검증: 성공.
- B 수정 뒤 A의 옛 receipt를 최초 수락하기: 비교은행 불일치로 거부.
- 상태 두 필드 변경·은행 배열 순서 변경: 의미 해시 유지.
- A 자체 내용·출처 identity·출처 metadata 변경: 과거 기록도 거부.
- 신규 수락의 injected grading/다른 현행 모델: 거부. 과거 모델 기록은 원시 결과 재현 조건으로 보존.
- 다른 이미 승인된 수정 세트를 남기고 A만 재검수: 전체 장부 선검사에서 거부. 기승인 ID를 needs_review로 되돌리는 것 역시 거부.
- 기존 source/정본/장부/후보/코드 바이트 보존, API 0, 실제 승급 0, receipt·장부 출력 0.

fixture는 기존 테스트 helper의 합성 판정을 메모리 안에서만 사용했다. 합성 model transport 표시는 gate 분기 검사용이며 실제 정확성·사람 확인의 증거가 아니다. 디스크에는 코드와 확인 결과만 저장했고, 합성 receipt나 승급 장부는 저장하지 않았다. 작은 2세트 fixture는 전체 은행 최소 주제/개수 검사를 호출하지 않으며 해당 계약은 CLI 소스로 확인했다.
