# audit_say 저장소 작업 지침

회계감사 학습 앱과 문제 제작·검토 자료를 함께 관리하는 저장소다. 아래 경로는 저장소 루트 기준이다. 사용자가 확정한 범위·정책을 이어받고 작업 중인 다른 변경을 보존한다.

## 작업에 맞는 지침

- 기준서형 독립 물음 또는 사례형 문제·물음의 신규 제작·추가·확장: [audit-question-author](.agents/skills/audit-question-author/SKILL.md)를 읽고 해당 유형의 제작 경로를 적용한다.
- 기존 문항·제작된 초안의 유형 구분, 주제 대응, 답안·배점 타당성·부분점수·실제 채점의 검증 또는 수정: [audit-question-review](.agents/skills/audit-question-review/SKILL.md)를 읽고 해당 유형의 검증 경로를 적용한다. 분류만 또는 배점만 검토하는 요청도 포함한다.
- 폴더·분석·wiki 관리: [자료 관리 규칙](docs/출제-검토-자료-관리.md)을 읽고, 바꾸는 묶음의 README와 [wiki SCHEMA](cpa_uploader/wiki/SCHEMA.md)를 확인한다. 이 작업만으로 문항 제작·승급을 시작하지 않는다.
- 앱·API·DB 코드 작업: [README](README.md), `package.json`, 해당 코드·테스트에서 계약을 확인한다. 문항 내용이나 채점 계약에 영향을 줄 때 관련 스킬을 추가한다.
- 물음 분류·독립 풀이·학습 DB·선택 제출: [물음별 학습 단위 계약](docs/물음별-학습-단위와-분류-계약.md)을 읽는다. 기준서형/사례형은 답안 `type`과 별개이며 모든 물음에 실제 요구내용의 주제를 하나 이상 연결한다.

스킬 이름을 사용자가 직접 쓰지 않아도 위 요청에 적용한다. 유형이 명시되지 않으면 먼저 물음별 사실 의존성을 판정하고 제작·검증 경로를 선택한다. 신규 초안은 제작 후 검토 스킬로 이어지며, 기존 문항의 분류·배점 수정만으로 신규 출제를 시작하지 않는다. 지침·스킬 정비만 요청된 경우에는 필요한 지침만 갱신한다.

## 유형 구분과 배점 원칙

- **기준서형**은 기준서 내용과 일반 적용 조건만으로 답할 수 있어야 한다. **사례형**은 주어진 사실을 해석·적용해야 답할 수 있어야 한다. 회사명이 있거나 판단을 묻는다는 이유만으로 사례형으로 분류하지 않는다. 사실을 지워도 같은 만점 답안이 성립하는지와 실제 득점 요건을 함께 확인한다.
- 사실관계가 있는 학습 문제에는 사례형 물음만 포함하고 기준서형은 단독으로 분리한다. 사례형은 부모 문제에 연결하며 물음별 여러 주제를 허용한다. 주제로 검색해도 그 사례의 모든 사례형 물음을 표시한다. 세부 형상과 과거 판본 보존은 학습 단위 계약을 따른다.
- **열거형**은 정답인 독립 요소마다 기본 1점, **서술형**은 독립적으로 인정할 수 있는 의미 단위마다 배점하여 부분정답 점수를 합산한다. **판단·근거형**은 판단과 근거를 구별해 배점하고, 근거·조치가 결론을 분명히 함축하면 판단을 인정한다. 학습 유형과 이 답안 형식을 혼동하지 않는다.
- 문장·글자·줄 수로 배점하지 않는다. 같은 의미를 중복 배점하거나 조건·수식어를 기계적으로 잘라 점수를 늘리지 않는다. 소수 부분점수 대신 충족한 독립 기준의 정수 점수를 유지한다. 명시적 반대 결론은 해당 판단 점수를 주지 않되 독립적으로 맞는 근거까지 일괄 감점하지 않는다.
- 제작·검증 모두 **물음마다 배점 타당성**을 확인한다. 요구 요소·부분정답·필요 서술량·추론 부담·비슷한 물음의 배점을 대조하고 유지/조정/분리와 이유를 기록한다. 요구가 과도하게 묶였으면 별도 물음으로 나눌지 검토하며 옛 총점 상한에 맞춰 요구를 합치지 않는다. 상세 절차는 [공통 배점 계약](docs/물음별-학습-단위와-분류-계약.md#배점과-물음별-타당성)을 따른다.

## 자료의 수정 위치

| 위치 | 역할 |
| --- | --- |
| `cpa_uploader/raw/` | wiki 기반·제작·검증 원자료와 출처 계보. 원본·추출본·보존 사본을 구분하고 수집 매니페스트로 추적 |
| `cpa_uploader/data/` | 현재 문제은행과 기존 출처 계약의 등록 입력. 편집 정본은 `cpa_question_sets_v3.authoring.json` |
| `cpa_uploader/analysis/question-elements/` | 원발문 추출·재수록 연결·수동 보정과 생성 빈도표 |
| `cpa_uploader/analysis/coverage/` | 수동 `links.json`과 생성 `registry.json`·`summary.md`·주제별 조회 |
| `cpa_uploader/analysis/reviews/` | 여러 문항·주제의 검토 장부와 당시 실행 증거 |
| `cpa_uploader/drafts/` | 개별 제작 배치의 초안·계획·출처 패킷·QA·검수 receipt |
| `docs/` | 사람이 읽는 정책·설계·계획·보고 이력 |
| `cpa_uploader/wiki/` | 현재 자료 탐색과 수동 출제 지침. 생성 페이지는 입력·생성기에서 갱신 |

확장자가 아니라 소유권에 따라 수정한다. 생성 JSON·Markdown의 수치나 표를 직접 고치지 않는다. 문항 수·점수·판본·검토 상태는 현재 입력에서 읽고 이 지침에 고정하지 않는다.

새로 확보하는 wiki 기반 자료와 제작·검증 출처는 먼저 `cpa_uploader/raw/`에 보존하고 원출처·판본·원래 경로·파일 해시와 추출 계보를 기록한다. 기존 파일은 과거 인용·receipt의 경로와 바이트를 유지한 채 raw 보존본에 연결한다. 수집만으로 공식성·판본 적합성·문항 검수 완료를 인정하지 않는다. 보존본과 현행 등록 입력의 관계는 [raw 안내](cpa_uploader/raw/README.md), 제작·검증 시 원문 대조는 [공통 출처 검증 지침](.agents/skills/audit-question-review/references/source-evidence.md)을 따른다.

## 출제 자료를 해석할 때

- [통합 현황](cpa_uploader/wiki/_meta/authoring-dashboard.md)에서 시작해 원발문·공식 근거·현재 은행과 초안까지 추적한다. 학습 순서는 OX 순서를 따르며 기존 주제·요소·문항 ID는 재번호화하지 않는다.
- 빈도는 구체 요구사항별로 집계하고 상위 주제 합계를 구분한다. 서로 다른 실제 출제는 각각 세며 교재 간 재수록만 제외한다. 기출·모의·연습 수록을 임의로 합산하지 않는다.
- 미연결·0회·낮은 문구 유사도는 미출제 확정이 아니다. 관계 검토, 문항 검수, 실제 채점, 사람 확인, 정본 수록·게시·운영 배포는 각각 확인한다.
- 관계를 바꾸면 [coverage 입력 계약](cpa_uploader/analysis/coverage/README.md)을 따른다. 오래된 관계는 의미를 다시 대조하며 해시만 새 값으로 바꾸어 검토를 대신하지 않는다.
- 날짜별 보고서는 당시 기록이다. 과거 원문·로그·receipt의 바이트·해시·판정을 보존하고 새 검토는 후속 증거로 남긴다. 이동 전 경로는 해당 `migration-manifest.json`으로 해석하고, 없는 파일은 미보관으로 표시한다.
- 의미검수와 사례 채점의 실제 모델 호출·주입 응답·미실행을 각각 확인한다. AI의 대리 검토를 사람 확인으로 기록하지 않는다. 과거 기록의 읽기 호환과 새 검수 수락은 별개다.
- 사례형은 주어진 사실과 연계해 답해야 하고 부모 사실이 필요하다. 기준서형은 사례 부모 없이 한 물음만으로 푼다. 새 출력의 `question_style`·`topic_ids`와 과거 판본의 분류 sidecar·봉인 메타데이터를 구분하며, 분류 이관을 위해 과거 원문·receipt를 다시 쓰지 않는다. 세부 형상·계보·선택 채점 경계는 학습 단위 계약을 따른다.

## 변경 후 검사

현재 명령은 `package.json`을 기준으로 하고 변경 범위에 맞춰 실행한다.

- 분석 입력·생성기를 바꿨으면 `npm run analysis:build` → `npm run analysis:check`. 이어 wiki 입력에도 영향을 주면 `npm run wiki:build` → `npm run wiki:check`.
- wiki 수동 지침·생성 입력을 바꿨으면 `SCHEMA.md`에 따라 필요한 재생성과 `npm run wiki:check`를 수행한다.
- 문항 수정·승급은 해당 스킬의 초안/정본/공개본 검증을 따른다. 빌드나 정적 검사 통과를 의미검수·실제 모델 채점·게시 완료로 보고하지 않는다.
- 채점 실행·응답 검증·증거 저장 오류를 학생의 감점으로 바꾸지 않는다. 사례를 고쳐도 유효한 원답안과 반례를 보존하며, 오류 분류·재시도·부분 기록·재실측은 [검토 스킬의 회귀 지침](.agents/skills/audit-question-review/references/regression-cases.md)을 따른다.
- 코드 변경은 관련 테스트·타입 검사·대상 lint로 확인한다. 커밋 시에는 `.githooks/pre-commit`의 타입·전체 테스트·분석 보존·wiki 검사를 따른다. 문서·스킬만 바꿨으면 링크·지침 충돌·스킬 형상을 확인하며 형식적인 전체 재빌드를 하지 않는다.
- 새 변경·실패·미해결 우려가 있을 때 검사를 추가한다. 실행한 검사와 미검증 범위를 구분해 보고한다.
- 여러 작업이 같은 공통 코드로 모델 검수·채점을 진행하면 코드 변경과 실측 시점을 조율한다. 확정한 파일 해시를 전달하고 실측 중에는 그 버전을 유지한다. 변경으로 중단된 실행의 판정 지시·입력·기존 증거를 보존하며 옛 실행 잠금의 해시만 바꿔 계속하지 않는다.

## 지침을 유지할 때

프로젝트 공통 규칙은 이 파일, 상세 자료 관리 규칙은 `docs/출제-검토-자료-관리.md`, 제작·검토 절차는 `.agents/skills/`에서 관리한다. Claude의 `CLAUDE.md`와 `.claude/skills/`는 공통 본문으로 연결한다. 같은 절차를 여러 본문에 복제하지 않고, 스킬 이름·설명을 바꿀 때만 대응 진입점과 `agents/openai.yaml`도 대조한다.

제작·검증 중 확인한 재사용할 규칙은 해당 스킬이나 이 파일에 반영하고, 판본별 원문은 raw, 실행별 결과는 검토 배치에 남긴다. wiki나 날짜별 보고서만 읽어야 필수 절차를 알 수 있게 두지 않는다. 사용자의 명시적 범위·정책을 우선하며 개별 사례를 확인 없이 보편 규칙으로 확대하지 않는다.
