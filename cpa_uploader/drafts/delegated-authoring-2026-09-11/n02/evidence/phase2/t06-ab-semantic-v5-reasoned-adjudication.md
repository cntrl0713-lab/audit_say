## 증적 예시와 직접 근거의 범위

T06-A Q2는 개선 통제와 그 통제의 실행을 확인할 흔적을 설계하게 한다. 모범답안과 c6/c8은 `등`으로 적정한 검증 흔적을 예시한다. 특정 법정 보존기간이나 반드시 보관할 폐쇄 목록을 묻지 않는다. 변경 전후 정보·독립 승인자·승인시점은 누가 어떤 계좌 변경을 승인했는지 확인하는 수단이고, 대사표·차이조사·독립 검토 기록은 지급·기록·대사의 견제가 수행되었는지 확인하는 수단이다.

315 보론3.20(`src-1d496d64105b41f915`, 등록 파일 L514–572)은 유효성을 확인하는 권한부여·승인, 차이 식별 후 조치하는 대사·검증, 특정인이 오류·부정을 저지르고 숨길 기회를 줄이는 업무분장과 소규모 기업의 보완 통제를 직접 설명한다. 315 A177(`src-69b976ccea32faf8a9`)은 특정 통제 적용에 대한 관찰, 문서·보고서 검사 등을 통한 실행 확인을 설명한다. 이는 사례별 기록 예시를 설계하는 근거이며 원문에 ‘변경 전후 계좌’라는 특정 명사가 그대로 있어야 하는 요구가 아니다.

c6/req6의 직접 연결이 보론3.20에만 집중된 것은 명시적 연결을 보완할 수 있는 지점이다. 그러나 A177이 세트에 실제 등록되어 있고 앞의 통제 목적과 사례가 결합된다. 따라서 불확실성을 ‘실제 출처가 없다’거나 ‘기록 의무를 창작했다’로 확정하지 않는다. 실측에서 c6의 대체 증적 답안을 원 예시 전체 누락으로 감점한 현상은 별도의 채점 범위 문제이며 [작성자 QA 조사](phase-two-v4-proposals/t06-a-v4-reasoned-adjudication.md)에 남겼다.

T06-A Q3의 req9는 315.26(d)(ii)(`src-8255896e6aab367667`)를 직접 인용하고, **criterion crit9의 source_ref_ids에는 26과 A177이 모두 있다.** 같은 receipt의 c9 단위도 A177이 관찰·검사를 직접 제시한다며 source_support pass였다. Q3 전체의 uncertain은 실제 연결이 없는 것이 아니라 requirement의 단일 인용만 보고 해당 criterion의 실제 연결을 충분히 합치지 못한 판단이다. 별도 계획 보완 시 단일 requirement 인용을 A177로 맞추는 방법은 가능하나 현재 고정 입력은 변경하지 않았다.

## A/B의 실행 확인 복습 관계

실제 공통 요구는 T06-A Q3/c9와 T06-B Q3/c7의 질문 외 관찰·검사이다. T06-A는 앞에서 설계한 지급 통제가 실제 존재·사용되는지 확인할 구체 절차와 상태(c10)를 묻고, T06-B는 설명만으로 실행과 기간 전체 운영효과성까지 확인했다는 결론을 평가하며 그 기간 확대의 한계(c8)를 추가한다. 사례와 둘째 명제의 목적은 다르지만 첫 명제는 복습이다.

두 version1 계획 모두 `pilot-06-003/sub2`의 설계·실행 범위를 사례에 적용하는 복습으로 명시한다. 원 주제계획의 T06-A Q3는 의도된 복습, T06-B Q2/Q3도 사례 적용 복습이라고 각각 명시한다. 둘 다 같은 정본의 c11(질문에 추가된 절차로 실행 여부 결정)을 복습하므로 서로 유사해지는 것은 원 설계에 내재한 관계다. 서로의 신규 ID를 각각 적지 않았다는 이유로 ‘복습 허용 범위를 넘었다’는 fail은 과도하다. 다만 **A/B 사이의 c9↔c7 직접 관계를 명시적으로 장부에 추가하고 신규 커버리지에 중복 산입하지 않는 것**은 좋은 문서 보완이다. 문항 삭제나 새 발문을 더 만드는 근거는 아니다.

모델 rationale의 `pilot-06-007/sub3/crit1`은 실제 ID가 아니다. 실제 ID는 **crit7**이며 비교은행에도 이를 확인했다. 유사성 자체가 틀렸다는 뜻은 아니지만 정확한 관계 대상은 정정해야 한다.

## T06-B 변경 작성·이관·확인의 집중

315 보론6.2(`src-7c3f3ebc114e489c97`, L632–763)는 변경 설계·프로그래밍·테스트·운영환경 이관의 관리, 변경 작성 권한과 운영환경 이관 권한의 분리를 직접 제시한다. A173(`src-650ca2254c12b5e48e`, L326–331)은 승인되지 않은 프로그램 변경 위험을 설명한다.

‘변경 후 결과 확인도 동일 개발자가 맡으며 별도의 독립 검토가 없다’는 기준서의 보편 의무를 인용한 문장이 아니라 **공통 지문의 명시된 사실**이다. 그 사실과 권한 미분리가 결합하면 부적절한 변경을 반영하고 자기 검토로 발견 가능성을 낮출 수 있다는 위험 연결은 타당하다. 실제 은폐가 일어났다고 확정하지 않으며 독립된 사후확인이 모든 기업에서 유일한 법정 통제라고 주장하지 않는다. 보론3.20의 업무분장이 오류·부정의 발생·은폐 기회를 줄인다는 직접 원칙도 같은 공식 파일에 존재한다. 이 보충 원칙이 T06-B source_refs에 별도 지정되어 있지는 않으므로 연결을 더 직접 만들 수는 있으나, 이미 등록한 IT 업무분장·무단 변경 원칙과 주어진 사례에서 도출하는 위험 자체를 fail로 볼 근거는 부족하다.

후속 조치는 총괄의 의미진단·관계 장부에 위 판단을 넘기는 것이다. 출처 인용이나 계획의 명료화를 채택할 경우 새 입력과 비교은행의 영향 범위를 먼저 정해야 하며, 현재 receipt를 수동 pass로 바꾸지 않는다.
